What is Section 4.4 about?

Programmers write conditions (predicates) in code — like if (a < b && c > d). They might accidentally use the wrong operator, wrong comparison sign, or make an arithmetic mistake. Predicate testing gives us a systematic, minimal way to generate test cases that are guaranteed to catch those mistakes.

Your notes cover the three worked examples for BOR-CSET (the core algorithm) plus the BRO constraint extension and fault propagation. That's exactly what this file teaches.

4.4.1 The Fault Model — What bugs are we targeting?

Before generating tests, we need to know what kind of bug we're hunting. The fault model defines three categories:

① Boolean Operator Fault

Wrong logical operator (∧ vs ∨), misplaced negation (¬), wrong parentheses, or wrong Boolean variable.

Example:

Correct: a < b ∨ c > d
Faulty: a < b ∧ c > d
② Relational Operator Fault

Wrong comparison sign: < written as ≤, == instead of <, etc.

Example:

Correct: a < b
Faulty: a == b
③ Arithmetic Expression Fault

An "off-by-ε" error in the arithmetic part of a relational expression. Three sub-types:

off-by-ε — exactly off by ε

off-by-ε* — off by ≥ ε

off-by-ε+ — off by > ε

⚠️
What the BOR-CSET procedure does NOT catch

Missing Boolean variable fault (e.g. coding a instead of a ∨ b) and extra Boolean variable fault (e.g. coding a ∨ b ∨ c instead of a ∨ b) are not detected by the procedures in this section.

4.4.3 BR Symbols & Predicate Constraints
The BR Symbol Set

BR = Boolean and Relational. The set of all allowed symbols is:

BR = { t, f, <, =, >, +ε, −ε }

Each BR symbol constrains one simple condition in a predicate:

SymbolApplied toMeaning (what the test must ensure)
tBoolean variable or expressionThe expression must evaluate to TRUE
fBoolean variable or expressionThe expression must evaluate to FALSE
<Relational expression e₁ relop e₂Test must make e₁ − e₂ < 0
=Relational expression e₁ relop e₂Test must make e₁ − e₂ = 0
>Relational expression e₁ relop e₂Test must make e₁ − e₂ > 0
+εRelational expression0 < e₁ − e₂ ≤ ε (just above equal)
−εRelational expression−ε ≤ e₁ − e₂ < 0 (just below equal)
Predicate Constraint — Definition

A predicate with n simple conditions (Boolean variables or relational expressions) has a predicate constraint that is a sequence of n BR symbols — one for each simple condition.

💡
Example

Predicate: pr : b ∧ r<s ∨ u≥v has 3 simple conditions: b, r<s, u≥v

A valid constraint: C = (t, =, >)

→ b must be true, r−s = 0, u−v > 0

→ Test: <b=true, r=1, s=1, u=1, v=0> satisfies this constraint.

True Constraints vs False Constraints

A constraint C for predicate pr is a true constraint if evaluating pr on any test that satisfies C gives TRUE.

It is a false constraint if it gives FALSE.

We split a constraint set S into: Sᵗ (true constraints) and Sᶠ (false constraints), so S = Sᵗ ∪ Sᶠ.

Set Products — Two Kinds You Must Know

Two set operations are used throughout the BOR-CSET algorithm:

× — Regular Cartesian Product

All possible pairs (a,b) where a∈A, b∈B.

A = {t, =, >} B = {f, <} A × B = {(t,f),(t,<),(=,f), (=,<),(>,f),(>,<)}

→ 6 pairs. Always unique.

⊗ — Onto (Minimal) Product

A minimal set of pairs such that every element of A and every element of B appears at least once.

A = {t, =, >} B = {f, <} A ⊗ B = {(t,f),(=,<),(>,<)} or {(t,<),(=,f),(>,<)} or ... (6 possibilities)

→ NOT unique! Pick any one.

🔑
Why ⊗ matters

BOR-CSET uses ⊗ (onto product) to keep the constraint set minimal. Using regular × would give too many test cases. The BOR, BRO, BRE procedures all use ⊗ when propagating through AND/OR nodes in the AST.

4.4.4 BOR, BRO, BRE — The Three Testing Criteria

These three criteria define what quality your test set must achieve. Think of them as progressively stronger guarantees:

BOR — Boolean Operator

A BOR-adequate test set guarantees detection of all single and multiple Boolean operator faults.

Leaf constraints: {t, f}

BRO — Boolean + Relational Operator

A BRO-adequate test set is likely to detect Boolean operator AND relational operator faults.

Leaf constraints (relational): {<, =, >}

BRE — Boolean + Relational + Expression

A BRE-adequate test set is likely to detect all three fault types including arithmetic off-by-ε.

Leaf constraints (relational): {+ε, =, −ε}

📏
Size of adequate test sets

If a predicate pr has n AND/OR operators:

→ Max size of BOR-adequate test set = n + 2

→ Max size of BRO or BRE-adequate test set = 2n + 3

This is much smaller than the brute-force 2ⁿ approach!

4.4.5 Procedure BOR-CSET — The Algorithm

This is the core algorithm your notes work through in all three examples. It generates a minimal BOR constraint set by walking the Abstract Syntax Tree (AST) of a predicate bottom-up.

🌳
What is an AST (Abstract Syntax Tree)?

It's a tree representation of a predicate. Leaf nodes = simple conditions (Boolean variables or relational expressions). Internal nodes = logical operators (AND, OR, NOT).

For a<b ∧ c>d: root = AND node, left leaf = a<b, right leaf = c>d.

Procedure BOR-CSET (Bottom-Up AST Traversal)
1
Label every LEAF node with its default BOR constraint set:
For every leaf: Sₙ = { t, f } → Sₙᵗ = { t }, Sₙᶠ = { f }
2
Traverse bottom-up, computing Sₙ for each internal node using these rules:
NOT Node
Sₙᵗ = Sₙ₁ᶠ Sₙᶠ = Sₙ₁ᵗ

Just swap: true set becomes false set and vice versa.

AND Node (N₁ AND N₂)
Sₙᵗ = Sₙ₁ᵗ ⊗ Sₙ₂ᵗ Sₙᶠ = (Sₙ₁ᶠ × {t₂}) ∪ ({t₁} × Sₙ₂ᶠ) where t₁ ∈ Sₙ₁ᵗ, t₂ ∈ Sₙ₂ᵗ

True: both sides must be true → onto product.
False: one side false while other true.

OR Node (N₁ OR N₂)
Sₙᶠ = Sₙ₁ᶠ ⊗ Sₙ₂ᶠ Sₙᵗ = (Sₙ₁ᵗ × {f₂}) ∪ ({f₁} × Sₙ₂ᵗ) where f₁ ∈ Sₙ₁ᶠ, f₂ ∈ Sₙ₂ᶠ

False: both sides must be false → onto product.
True: one side true while other false.

3
The constraint set at the root node is your final BOR constraint set. Generate test cases that satisfy each constraint.
🧠
Memory trick for AND vs OR rules

AND: To be TRUE, BOTH sides must be true (use ⊗). To be FALSE, ONE side is false while the other is true (use ×).

OR: To be FALSE, BOTH sides must be false (use ⊗). To be TRUE, ONE side is true while the other is false (use ×).

The ⊗ always goes on the "both must agree" side!

4.4.5 BRO-CSET and BRE-CSET — Quick Reference

Same procedure as BOR-CSET — only the leaf node labeling (Step 1) changes:

BOR-CSET Leaves
All leaves: Sₙ = { t, f }

Simple — just true/false. Targets Boolean operator faults only.

BRO-CSET Leaves
Boolean var: Sₙ = {t, f} Relational: Sₙ = {<, =, >}

Relational expressions get 3-way split. Targets Boolean + relational faults.

BRE-CSET Leaves
Boolean var: Sₙ = {t, f} Relational: Sₙ = {+ε, =, −ε}

Detects off-by-ε arithmetic errors on top of Boolean + relational faults.

The true/false split of BRO leaf constraints depends on the relational operator:

≥{(>),(=)}{(<)}
={(=)}{(<),(>)}
<{(<)}{(=),(>)}
≤{(<),(=)}{(>)}
4.4.8 Fault Propagation
Core Concept

A fault in a predicate propagates to the root of the AST if evaluating the correct predicate pₒ and the faulty predicate pᶠ on the same test case t gives different results:

Fault propagates ⟺ pₒ(t) ≠ pᶠ(t)

A test t that satisfies this is called a fault-revealing or error-revealing test.

Why Some Tests Don't Reveal Faults

Even a theoretically BOR-adequate test set can fail to reveal a bug in practice. Reasons:

① The faulty statement is unreachable (infeasible path).

② Another bug in the program masks the first bug.

③ The condition feeding the predicate is indirectly constrained by other inputs.

⚡
Key exam point

BOR/BRO/BRE-adequate test sets guarantee detection only for faults in the predicate itself. They cannot guarantee detection if the predicate is unreachable or if there are masking faults elsewhere in the program.

Size Advantage — Why Predicate Testing beats Brute Force

For predicate with n AND/OR operators and Boolean variables:

Brute Force (Enumerate All)
Test cases: 2ⁿ

For n=3: 8 test cases

BOR/BRO/BRE-CSET
BOR: n + 2 tests BRO/BRE: 2n + 3 tests

For n=3: 5 test cases (BOR) or 9 max (BRO/BRE)

Growth is linear in n, not exponential — this is the key advantage.

Step-by-Step Exam Checklist
1
Parse the predicate. Identify leaf nodes (relational expressions / Boolean variables) and operator hierarchy. Draw the AST.
2
Label leaves: BOR → {t,f} | BRO → {<,=,>} | BRE → {+ε,=,−ε}. Split into Sᵗ and Sᶠ using the relop table.
3
Traverse bottom-up. At each node apply the NOT / AND / OR rules. Maintain Sᵗ and Sᶠ separately.
4
Combine Sᵗ ∪ Sᶠ at the root. This is your final constraint set.
5
Assign actual test values to each constraint. Verify by evaluating the predicate against each test.
6
(If fault propagation asked): Compare pₒ(t) vs pᶠ(t) for each test. A fault is detected where they differ.
