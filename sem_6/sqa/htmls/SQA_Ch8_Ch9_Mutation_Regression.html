Chapter 8 — Mutation Testing
📌
What Ch.8 is about — one sentence
You have a program P and a test set T. P passes all tests. But how good is T? Mutation testing answers this by deliberately introducing bugs (mutants) into P and checking whether T is strong enough to detect them.
8.1 Introduction — What is Mutation Testing?
Core Idea (from your Image 2)

Your notes ask: "What is adequacy? What is program mutation?"

Test adequacy = a measure of how "good" your test set is. A test set T is adequate w.r.t. some criterion if it meets the defined quality threshold for that criterion.

Program mutation = slightly changing a program P to produce a mutant P'. We then ask: does T catch the difference between P and P'? If yes, T is "good" at detecting that kind of fault.

Sunny Day Scenario

P and P' behave the same → T passes both. This is the success scenario.

Rainy Day Scenario

P and P' behave differently → T should expose this. If T fails to, T is inadequate.

8.2 Mutation & Mutants — Key Definitions
Vocabulary You Must Know (Image 2)
P'

A mutant of program P. Obtained by making one small syntactic change to P.

P is called the parent of P'.

t → single test

One test case.

T = set of all test cases (the test suite).

Kill a Mutant

Test t kills (= distinguishes) P' if: P(t) ≠ P'(t).

That test has revealed a behavioral difference.

Live Mutant

A mutant that has NOT been killed by any test in T yet. Still "alive."

First-Order vs Higher-Order Mutants

First-order mutant: ONE change made to P. These are standard in practice.

Higher-order mutant: two or more changes made simultaneously. Rarely used — exponentially more mutants, harder to manage.

⚠️
Why first-order only? Because the number of second-order mutants explodes. For a 28-line Fortran program (FIND), there are already 528,906 second-order mutants. Impractical.

Equivalent Mutants (Images 2, 5, 6)

If there is NO test case t in the entire input domain of P such that P(t) ≠ P'(t), then P' is equivalent to P.

Equivalent mutants cannot be killed — ever. They are removed from the mutation score calculation.

🔴
The Undecidable Problem (Image 6)

Determining whether a mutant is equivalent to its parent is undecidable in polynomial time — i.e., no program can decide this in bounded time for all cases. That is why we handle it manually or heuristically.

Decidable: there exists a polynomial-time program that can say yes/no. Undecidable: no such program exists in general.

From your Image 5 (the algebra to check equivalence):

P computes: x - y m₂ computes: x + y ← mutant Are they equivalent? Set x-y = x+y → 0 = 2y → y ≠ 0 (they differ when y ≠ 0) → NOT equivalent!

So test t₃ with y ≠ 0 will kill m₂. Your notes note: "by t₃ all mutants are killed." ✅

💡
Misconception (Images 6, 7)

A common misconception: "if a mutant is not killed by T, it must be equivalent." Wrong. It might just be that T is weak and doesn't contain the right test. Always check algebraically whether the mutant's output domain can ever differ from P's.

The "missing else" example in Image 7 is precisely this: the mutation creates a "missing path" — a code path that P has but the mutant doesn't, or vice versa. That's a structural change, not necessarily semantic equivalence.

8.3 Test Adequacy Using Mutation — Mutation Score

This is the full process from Image 3 and the core of Chapter 8. Memorize the formula and process.

Notation (Image 3)
m = Total Mutants

All mutants generated from P. Also written |K| in some notations.

K₁ = Killed Mutants

Mutants that have been distinguished (killed) by at least one test in T.

K₂ = Live Mutants

Mutants not yet killed. Could be equivalent or just need better tests.

e = Equivalent Mutants

Proven to be equivalent to P. Excluded from denominator of MS.

Note: K - K₁ = remaining live (non-killed) mutants. If K - K₁ = 0, all are killed.

MS = K₁ / (K − e)
Mutation Score = Killed Mutants / (Total Mutants − Equivalent Mutants)
K₁ = distinguished (killed)
K = total generated
e = equivalent (excluded)
✅
MS = 1 → Perfectly adequate test set

All non-equivalent mutants have been killed. T is mutation-adequate.

MS < 1 → T is inadequate. You need more test cases.

Full Procedure: Test Adequacy Assessment (Images 3, 4)
12-Step Mutation Assessment Process (Figure 8.1 in book)
1
Execute P against all tests in T. Record P(t) for all t ∈ T. Ensure P is correct — mutation testing starts only after P passes all its tests.
2
Generate mutants. Apply mutation operators to P. All mutants are initially "live" → set L.
3
All mutants considered? If yes → go to Step 11. If no → pick next mutant.
4
Remove next mutant M from L. Now we try to distinguish it.
5
All tests considered for M? If yes → M is not killed → go to Step 10 (put back in L).
6
Select next test case t from T.
7
Execute M against t. Compute M(t).
8
Is P(t) = M(t)? If yes → same behavior → go back to Step 5. If no → M is distinguished!
9
M is distinguished → add to set D. Stop running M against remaining tests. Go to Step 3.
10
10
Put M back in L as live. M was not killed by any test in T.
11
Identify equivalent mutants. Check remaining live mutants — prove algebraically if any are equivalent. Put them in set E.
12
Compute MS = |D| / (|L| + |D|). This is your test adequacy score.

Test Enhancement Using Mutation (Image 3)

From your notes: "non-equivalent live ke adequacy enhance kry ga. If MS is 1 then means mutants are killed. Existing test nay sary mutants ko kill kr deya. Ab new add tb gay TC."

Translated precisely:

① If MS = 1 → all non-equivalent mutants killed → T is adequate → done.

② If MS < 1 → some live mutants remain → add new test cases to kill them → recompute MS.

③ If MS < K₁/(K-e) → we make new test cases.

Condition to ADD new tests: 1 < K₁ / (K - e) is FALSE → i.e. MS < 1 → live mutants still exist → enhance T with new test cases that kill the remaining live mutants
8.4 Mutation Operators & Competent Programmer Hypothesis
What is a Mutation Operator? (Image 8)

A mutation operator is a rule that systematically generates mutants from a program. It defines what kind of change to make. Examples:

ROR — Relational Operator Replacement: change < to ≤, > to <, etc. AOR — Arithmetic Operator Replacement: change + to -, * to /, etc. ABS — Absolute Value Insertion: wrap expression e in abs(e) COR — Conditional Operator Replacement: change && to ||, etc. CCR — Constant Constant Replacement: replace constant c with constant d
Competent Programmer Hypothesis (Image 8)

Competent programmers write programs that are close to correct — only a few mutations away from a correct program.

"As programs eitny ga k a few mutants away hoga" (your notes)

Coupling Effect (Image 8)

First-order mutants, once detected, can also detect many higher-order mutants — they are "coupled."

"First order mutants (once detect ksny way) test cases hai." (your notes)

Mutation Operators: Language Dependent (Image 8)

Mutation operators are specific to the programming language. The operators for C are different from Java.

For C / Fortran

Operators like ABS, AOR, ROR, COR, etc. — targeting arithmetic and relational changes.

Tools: Mothra (mentioned in your Image 8)

For Java (Image 8)

Additional operators for: polymorphism, dynamic binding, method overloading.

Tools: muJava, PIT (open source, Image 8)

Mutation Testing at Different Levels (Image 8)

Unit Level

Mutate individual functions/methods. Most common.

Class Level

Mutate classes — test object-oriented features: polymorphism, inheritance.

System Level

Mutate integration points — test how components interact.

8.3.4 Distinguishing a Mutant — 3 Conditions (Images 5, 6)
🎯
This is a frequently asked exam topic
Your Image 6 says: "Distinguishing a mutant: ① Reachability ② Infection ③ Propagation"

A test t distinguishes mutant M from parent P if and only if ALL THREE conditions hold:

① C₁: Reachability

The mutated statement must be executed during the test run.

If the mutated line is never reached, the mutation can never be detected.

Image 6: "Is line tak ana reachability (test case k through a jata hai)"

② C₂: Infection

After the mutated statement executes, the program state must differ between P and M.

Image 6: "Program execution sy bad wall state equal na ho" (state must NOT be equal)

③ C₃: Propagation

The state difference must propagate to the output. Different internal states that produce the same output still don't distinguish.

Image 6: "Sin and sout ka difference agox program tuk a jay tou esay propagation kshty hain"

Chapter 9 — Regression Testing
📌
What Ch.9 is about — one sentence
You have a working program P and a test set T. You modify P to get P'. You can't run all tests again (time/cost). Which subset of T do you re-run to ensure the unchanged parts of P still work in P'?
9.1 What Is Regression Testing? (Image 9)
Definition

Regression testing: retesting a modified program P' to ensure that code carried over unchanged from P continues to behave correctly.

The word "regress" = return to a previous, worse state. Regression testing prevents that from happening undetected.

Corrective RT

Testing P' obtained by fixing bugs in P.

Progressive RT

Testing P' obtained by adding new features to P.

Terminology: T is split into 3 categories (Image 9 + Image 1)
SetNameMeaningRe-run?
TrRegression subsetTests that test functionality CARRIED OVER from P to P'✅ YES
TuRedundant testsTests that don't traverse any modified portion of P'Maybe not
ToObsolete testsTests that are no longer valid for P' (input format changed, etc.)❌ NO
TdDevelopment testsNEW tests for newly added functionality in P'✅ YES (new)

The test set for P' is: T' = Tr ∪ Td

Test Selection Techniques (Image 9)

Your notes: "Test selection techniques: ① Execution tree ② Extract test vector ③ Syntax trees (④ u/n)"

9.4.1 Test All

Run T − To. Safest. Most expensive. Used in practice when time allows.

9.4.2 Random

Randomly sample from T − To. Cheap but unreliable.

9.4.3 Modification-Traversing

Only select tests that traverse modified code. Needs execution trace + syntax trees. SAFE.

9.4.4 Minimization

Further reduce Tr by removing redundant tests. NOT necessarily safe.

9.4.5 Prioritization

Rank tests by criticality. Select top-k when resources limited.

9.2.1 Test Revalidation (Image 1)

Check which tests from T are still valid for P'. A test becomes obsolete (To) if:

→ Input format changed for P'

→ Expected output changed

→ Feature removed from P'

Valid remaining tests = Tu ∪ Tr (the non-obsolete set).

9.2.3 Test Sequencing (Image 9)

Order of test execution matters for stateful applications (banking, SATM).

Example: to test Withdraw, you must first run Deposit — otherwise the account balance is 0 and Withdraw fails trivially.

Test sequencing ensures P' is in the correct state when each test runs.

9.2.5 Output Comparison (Image 9)

After execution, compare P'(t) with expected output. Automated tools do this. Your Image 9 shows "error collection ← output" arrow.

Key challenge: the oracle problem — knowing what the correct output should be. In regression testing, the oracle is usually P(t) recorded earlier, or the spec.

Control Flow Graph (CFG) — Basics

A CFG G = (N, E) represents a program's flow. Each node N = one basic block. Edges E = control flow.

Start = first node. End = last node.

Notation: main.3 = node 3 in main's CFG. g1.2 = node 2 in function g1's CFG.

Execution Trace (Image 10)

When P executes against test t, the execution trace = sequence of nodes visited in the CFG.

test(n) = the set of all tests that traversed node n. Also called the test vector of node n.

Syntax Trees & Node Equivalence (Images 1, 9)

Image 1 says: "Both nodes have same syntax → equivalence."

Each node in the CFG has a syntax tree representing the code in that basic block. Two nodes n (from P) and n' (from P') are equivalent if their syntax trees are identical — meaning the code in that block hasn't changed.

Image 1 also says: "T' → changes waly eimey ay gay" = T' (the selected regression tests) will contain only those tests that traverse CHANGED (non-equivalent) nodes.

💡
Key insight on syntax tree equivalence

If node n in G and node n' in G' have the same syntax tree → that code is UNCHANGED → tests traversing only this node need not be selected.

If syntax trees differ → code CHANGED → all tests in test(n) are selected for regression.

Function calls require checking the CFGs of the called functions recursively!

Procedure SelectTests (Image 1 + Image 9 methods list)
SelectTestsMain — Algorithm for Regression Test Selection
1
Set T' = Ø. Unmark all nodes in G (CFG of P) and all child CFGs.
2
Call SelectTests(G.Start, G'.Start) — compare from the start nodes of P and P'.
3
T' (the output) is the regression test set for P'.
SelectTests(N, N') — Recursive Comparison
1
Mark node N (to avoid revisiting).
2
If N and N' are NOT equivalent (different syntax trees): T' = T' ∪ test(N). Return. (All tests that ever visited this changed node are selected.)
3
Let S = successor nodes of N in G.
4
For each successor n in S:
4.1 If n is already marked → return (avoid cycle).
4.1.1 Let l = edge label (t, f, or empty).
4.1.2 Find n' = corresponding node in G' with same label.
4.1.3 Recurse: SelectTests(n, n').
5
Return.
