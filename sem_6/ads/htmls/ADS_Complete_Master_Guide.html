Chapter 31

Data Warehousing Concepts

31.1 What is a Data Warehouse?

Inmon's Definition (1993) — MEMORISE THIS A data warehouse is a subject-oriented, integrated, time-variant, and nonvolatile collection of data in support of management's decision-making process.

The Four Properties (S·I·T·N)

  • Subject-oriented: Organised around major subjects of the enterprise (customers, products, sales) — NOT around application areas (invoicing, stock control). Purpose: decision support, not transaction processing.
  • Integrated: Data comes from multiple inconsistent enterprise-wide sources. Must be made consistent to present a unified view. Example: one system stores "M/F", another stores "Male/Female" — must be standardised.
  • Time-variant: Data is accurate and valid at a point in time or time interval. DW stores historical snapshots — unlike OLTP which only holds current data. Time is always associated with every record.
  • Nonvolatile: Data is not updated in real-time. New data is added as a supplement, not as a replacement. Once loaded, it stays. No real-time inserts/deletes/updates by end users.

⚡ Exam Shortcut

  • SITN = Subject-oriented, Integrated, Time-variant, Nonvolatile
  • The ultimate goal: integrate enterprise-wide corporate data into a single repository for queries, reports, and analysis.
  • Bill Inmon = "Father of Data Warehousing"
  • Original concept by IBM = "Information Warehouse"

31.1.3 Benefits of Data Warehousing

  • Potential high ROI: IDC study reported 401% three-year ROI average.
  • Competitive advantage: Gives decision-makers access to previously untapped information on customers, trends, and demands.
  • Increased productivity: Creates integrated, consistent, subject-oriented historical data — lets decision-makers perform more accurate analysis.

31.1.5 Problems of Data Warehousing

  • Underestimation of resources for data ETL
  • Hidden problems with source systems
  • Required data not captured
  • Increased end-user demands
  • Data homogenization
  • High demand for resources (disk space for large fact tables)
  • Data ownership issues
  • High maintenance
  • Long-duration projects
  • Complexity of integration

31.3 ETL — Extract, Transform, Load

Extraction

Targets data sources (OLTP DBs, spreadsheets, ERP files, web logs). Copies extracted data to ODS or Staging Area (SA). Complexity depends on how different/similar source systems are.

Transformation

Applies rules/functions to extracted data. Includes: data summations, encoding, merging, splitting, calculations, creation of surrogate keys. Output: clean, consistent data ready for analysis.

Loading

Loads transformed data into the warehouse. Additional constraints (uniqueness, referential integrity, mandatory fields) applied. Data may be forwarded to data marts. Key issues: frequency of loading, effect on DW availability.

⚡ ETL Key Fact

ETL is the most time-consuming part of DW projects. ETL tools also offer: data profiling, data quality control, and metadata management.

31.3.3 Metadata

Metadata is "data about data." Three key uses:

  • ETL metadata: Maps source data to warehouse — source field IDs, types, locations, transformations applied.
  • Warehouse management metadata: Describes every object in the DB (tables, indexes, views, constraints, aggregations, partitions).
  • Query management metadata: Helps query manager direct queries + generates query profiles per user/group.

Major integration challenge: synchronising metadata between different vendor tools. Solution: OMG's Common Warehouse Metamodel (CWM).

31.4 Data Mart

Definition A database containing a subset of corporate data to support the analytical requirements of a particular business unit or group of users sharing the same business process.

Kimball vs Inmon on Data Marts

  • Kimball: Data mart = physical implementation of a single star schema for one business process. Multiple data marts → integrate → form the EDW.
  • Inmon: Data mart = supports requirements of a particular business unit (e.g., Sales dept). Data mart receives data FROM the EDW.

Reasons for Creating a Data Mart

  • Gives users access to data they need most often
  • Provides data in the format the business unit needs
  • Improves response time (less data to access)
  • Simpler ETL process (less data)
  • Lower cost than full EDW
  • Users more clearly defined → easier to get project support

31.5 Temporal Databases

Data warehouses are temporal databases — they store historical data with time associations.

  • Valid time: When a fact is true in the real world (business perspective). "What was the rent for PA14 on 25 Jan 2012?"
  • Transaction time: When a transaction was made on the database (system perspective). "What did the DB show the rent was on 25 Jan 2012?"
  • Bi-temporal database: Uses both valid time and transaction time.
  • Slowly Changing Dimension (SCD): When dimension data changes over time — must decide how to handle. Type 2 = add new record (most common in DW).

32.4 Dimensionality Modeling — Core Design Technique

Dimensionality Modeling A logical design technique that presents data in a standard, intuitive form for high-performance access. Every dimensional model (DM) has a fact table (composite PK) surrounded by dimension tables (simple PKs that are components of the fact table's composite PK).

Three Schema Types

SchemaDefinitionDimension tables
Star SchemaFact table in center surrounded by denormalised dimension tablesDenormalised (flat, redundant)
Snowflake SchemaFact table in center surrounded by normalised dimension tablesNormalised (dimensions can have sub-dimensions)
Starflake SchemaMix of denormalised star and normalised snowflake schemasSome normalised, some denormalised
STAR SCHEMA (property sales example): ───────────────────────────────────────────────────────── [Time] [Branch] [Staff] \ | / \ | / ──── [PropertySale] ──── ← FACT TABLE (centre) (offerPrice, composite PK = all FK refs sellingPrice, + own key saleCommission, saleRevenue) / | \ / | \ [Owner] [PropertyForSale] [ClientBuyer] SNOWFLAKE: Branch → [City] → [Region] (dimension has sub-dimensions) ─────────────────────────────────────────────────────────

Fact Table Rules

  • Contains ONE or more numerical measures (facts) per record
  • Facts should be numeric and additive — DW applications aggregate hundreds/thousands of records at a time
  • Composite primary key made up of foreign keys to all dimension tables
  • Fact tables are extremely large relative to dimension tables
  • Treat as read-only data (facts about past events don't change)

⚠️ Badly Structured Fact Table (from Ch 32 — could be an exam question)

A fact table is badly structured if it contains:

  • Non-numeric facts (e.g., promotionName, staffName)
  • Non-additive facts (e.g., monthlyRent — an average rate, not additive across records)
  • Facts at different granularity (e.g., lastYearRevenue is at a different level than the per-lease grain)

Dimension Table Rules

  • Contain descriptive textual information
  • Simple (non-composite) primary key
  • Attributes used as constraints in DW queries (filter, slice, group)
  • Generally much smaller than fact tables

Surrogate Keys — Why They Exist

In a DM, all natural keys (e.g., branchNo from the OLTP system) are replaced with surrogate keys (e.g., branchID — a simple integer). Every join between fact and dimension tables uses surrogate keys.

Benefit: Gives the DW independence from the OLTP system. If OLTP changes its natural keys, the DW is unaffected.

32.4.1 DM vs ER Model

  • ER model: Goal = remove redundancy (normalise). Best for OLTP. An enterprise ER model can have hundreds of tables with many joins — inefficient for ad hoc analysis.
  • DM (Star schema): Goal = high-performance, intuitive analytical access. Denormalised. One ER model normally decomposes into multiple DMs.
  • Multiple DMs are associated through shared (conformed) dimension tables.

32.5 Kimball's Dimensional Modeling Stage — 4 Steps

Phase I: Create high-level DM using these four steps:

1

Select Business Process

Choose the subject for the data mart (e.g., property sales, property rentals). First data mart should: be most deliverable, answer most commercially important questions, and establish reusable/conformed dimensions. Best choice = sales/finance (accessible + high quality data).

2

Declare Grain

The grain determines what one fact table record represents. Example: "individual property sale." Only after grain is chosen can dimensions be identified. Recommendation: lowest level of detail available. Grain of fact table determines grain of each dimension table.

3

Choose Dimensions

Dimensions set context for asking questions about facts. Identify dimensions in sufficient detail at the correct grain. Dimensions that appear in more than one DM = conformed dimensions. Conformed dimensions must be exactly the same OR one is a mathematical subset of the other.

4

Identify Facts

All facts must be at the grain level. Facts must be numeric and additive. Non-numeric, non-additive, or wrong-granularity items → do NOT belong in the fact table.

Phase II: Identify Dimension Attributes

Add attributes identified in business requirements analysis. The usefulness of a DM = scope and nature of dimension attributes (they govern how data is viewed for analysis).

32.5.2 Slowly Changing Dimensions (SCD)

Dimensions like "Branch" or "Staff" change slowly over time (address changes, name changes). How do we handle this in the DW?

Type 1 — Overwrite

Changed attribute simply overwrites the old value. No history preserved. Simple but loses historical accuracy.

Type 2 — New Record ✓ (most used)

Changed attribute causes a NEW dimension record to be created. Old record stays. History is fully preserved. Used in DW temporal data scenarios.

Type 3 — Alternate Attribute

Changed attribute causes an alternate attribute column to be added so both OLD and NEW values exist simultaneously in the same record.

Conformed Dimensions & Fact Constellation

  • Conformed dimension: A dimension shared across multiple DMs/data marts (e.g., Time, Branch). Enables drill-across queries.
  • Drill-across queries: Allow data from different fact tables to be analysed together in the same query.
  • Fact constellation: A dimensional model with MORE than one fact table sharing one or more conformed dimension tables. Represents the full EDW.

⚡ DW Design Quick Reference

  • Star = fact + denormalised dimensions
  • Snowflake = fact + normalised dimensions
  • Starflake = mix of both
  • Surrogate key = simple integer replacing natural key
  • Grain = what one fact record represents (lowest level possible)
  • Conformed dimension = shared across multiple data marts
  • Fact constellation = multiple fact tables + shared dimensions = full EDW
  • SCD Type 2 = new record created when dimension changes (DW default)
Chapter 33

OLAP

33.1 What is OLAP?

OLAP Definition Online Analytical Processing (OLAP) is the dynamic synthesis, analysis, and consolidation of large volumes of multidimensional data. It uses a multidimensional view of aggregate data to provide quick access to information for advanced analysis.

OLAP sits on TOP of the data warehouse. Together: DW + OLAP + Data Mining = Business Intelligence (BI) technologies.

⚡ OLAP vs General Query Tools

General query tools answer "who?" and "what?" questions. OLAP goes further — it answers "why?" questions. Example:

  • Query tool: "What was the total revenue for Scotland in Q3 2013?"
  • OLAP: "WHY was the total revenue for Scotland in Q3 2013 higher than other quarters?"

33.2 Key Features of OLAP Applications

  • Multidimensional views of data: Core requirement. All dimensions must be treated equally. Users can analyse data across any dimension at any level of aggregation.
  • Support for complex calculations: Moving averages, percentage growth, forecasting. Mechanisms should be nonprocedural and easy for users.
  • Time intelligence: Comparing this month vs last month, year-to-date, period-over-period. Time is the most common analytical dimension.

33.3 Multidimensional Data Model

Data Cube

Multidimensional data (facts + dimensions) is best visualised as a data cube:

  • 2D data (location × time): fits naturally in a matrix
  • 3D data (type × location × time): fits in a 3D cube — cells contain the fact values
  • n-D data: In OLAP, a data cube is an n-dimensional structure. Represented as a lattice of cuboids.

Example: cell where type='Flat', city='Glasgow', quarter='Q1' → revenue = 15,056.

33.3.2 Dimensional Hierarchy

Dimensions are hierarchical. Example hierarchies:

  • Location: zipCode → area → city → region → country
  • Time: day → month → quarter → year   OR   day → week → season → year

Hierarchies enable roll-up (aggregate up) and drill-down (detail down) operations.

33.3.3 Multidimensional Operations — The Five Operations

🔼 Roll-Up

Aggregates data by moving UP the dimensional hierarchy (zipCode → city) OR by dimensional reduction (4D → 3D by dropping one dimension).

🔽 Drill-Down

Reverse of roll-up. Reveals detailed data. Moves DOWN the hierarchy (city → area → zipCode) OR by dimensional introduction (3D → 4D).

🍕 Slice

Selection on ONE dimension. Example: show all revenue where type = 'Flat'. Creates a "slice" through the cube on one axis.

🎲 Dice

Selection on TWO OR MORE dimensions. Example: revenue where type='Flat' AND time='Q1'. Creates a sub-cube.

🔄 Pivot

Rotates the data to provide an alternative view of the SAME data. Example: swap x-axis (location) with y-axis (time). Does not change the data — only the perspective.

⚠️ Common Confusion: Slice vs Dice

Slice = 1 dimension constrained. Dice = 2+ dimensions constrained. Both are sub-operations of "slice and dice" but they are distinct.

33.4 OLAP Tools

33.4.1 Codd's 12 Rules for OLAP (1993)

E.F. Codd (same Codd of relational DB fame) formulated these as requirements for OLAP tool selection:

1
Multidimensional conceptual view — model must match enterprise dimensions
2
Transparency — underlying DB and architecture invisible to users
3
Accessibility — access all data from heterogeneous sources (relational, nonrelational, legacy)
4
Consistent reporting performance — no degradation as dimensions/aggregations grow
5
Client-server architecture — optimal performance, flexibility, scalability
6
Generic dimensionality — all dimensions equal in structure and operational capabilities
7
Dynamic sparse matrix handling — efficient storage of empty cells (nulls)
8
Multi-user support — concurrent access by group of users
9
Unrestricted cross-dimensional operations — auto roll-up across dimensions
10
Intuitive data manipulation — point-and-click and drag-and-drop actions on cube cells
11
Flexible reporting — any view of data in any row/column/cell arrangement
12
Unlimited dimensions and aggregation levels — no artificial restrictions

33.4.3 Categories of OLAP Servers

MOLAP — Multidimensional OLAP

Uses specialised multidimensional data structures (MDDBMSs) and array technology. Data pre-aggregated for fast queries. Best for specific decision-support applications. Issues: limited data volume, requires specialised skills.

ROLAP — Relational OLAP

Uses relational DBMS with a metadata layer. Creates multidimensional views from 2D relations. No static multidimensional structure needed. Fastest growing. Issues: performance with complex queries, needs middleware.

HOLAP — Hybrid OLAP

Combines ROLAP and MOLAP. Delivers data from DBMS or via MOLAP server to desktop as a cube. Issues: significant data redundancy, consistency problems between users, limited data capacity.

DOLAP — Desktop OLAP

Stores OLAP data in client-based files. Multidimensional engine runs on the client. Small extracts of data held on client machines. Issues: security (data physically extracted), deployment effort, thin-client trend.

⚡ Quick OLAP Architecture Memory Aid

  • MOLAP: M = Multidimensional storage (own proprietary structure)
  • ROLAP: R = Relational storage (existing RDBMS + metadata layer)
  • HOLAP: H = Hybrid of MOLAP + ROLAP
  • DOLAP: D = Desktop (client-side cube, small extracts)

33.5 OLAP Extensions to SQL

SQL was extended with OLAP functions in SQL:2003 (IBM + Oracle jointly proposed) and enhanced in SQL:2008 and SQL:2011. Two key feature sets:

ROLLUP — Subtotals at Multiple Levels

ROLLUP Creates subtotals at n+1 levels (where n = number of grouping columns). Rolls up from most detailed level to a grand total, following the column list order. 
SELECT propertyType, yearMonth, city, SUM(saleAmount) AS sales
FROM Branch, PropertyForSale, PropertySale
WHERE ...
GROUP BY ROLLUP(propertyType, yearMonth, city);
-- With n=3, produces 3+1 = 4 aggregation levels:
-- 1. propertyType + yearMonth + city (detailed)
-- 2. propertyType + yearMonth (subtotal across cities)
-- 3. propertyType (subtotal across yearMonth and city)
-- 4. Grand total

CUBE — All Possible Subtotal Combinations

CUBE Generates ALL possible subtotals for a data cube with specified dimensions. With n columns, produces 2n combinations (vs ROLLUP's n+1). 
GROUP BY CUBE(propertyType, yearMonth, city);
-- With n=3: 2³ = 8 levels of aggregation
-- Includes everything ROLLUP produces PLUS additional cross-combinations
-- E.g., city totals for combined property types (not in ROLLUP)

When to use CUBE vs ROLLUP:

  • Use ROLLUP when dimensions have a natural hierarchy (year → month → day) — less meaningful combos
  • Use CUBE for cross-tabular reports with independent dimensions (propertyType × yearMonth × city)

33.5.2 RANK and DENSE_RANK

SELECT branchNo, SUM(saleAmount) AS sales,
       RANK() OVER (ORDER BY SUM(saleAmount) DESC) AS ranking,
       DENSE_RANK() OVER (ORDER BY SUM(saleAmount) DESC) AS dense_ranking
FROM ...
GROUP BY(branchNo);
FunctionBehaviour on Ties
RANK()Leaves gaps. Three tied at 2nd place → next rank is 5th.
DENSE_RANK()No gaps. Three tied at 2nd place → next rank is 3rd.

Windowing — Moving Averages & Sums

AVG(SUM(saleAmount)) OVER (ORDER BY yearMonth ROWS 2 PRECEDING)
-- Calculates 3-month moving average (current + 2 preceding months)

Moving windows can compute: cumulative sums, moving averages, moving min/max. Returns a value for each row based on other rows in the window.

Ch31🔥 HotDiscuss what is meant by subject-oriented, integrated, time-variant, and nonvolatile when describing a data warehouse.
  • Subject-oriented: Organised around major business subjects (customers, products, sales) rather than application areas (invoicing, stock control). Supports decision-making, not transaction processing.

  • Data age: OLTP = current; DW = historical
  • Data latency: OLTP = real-time; DW = depends on ETL refresh cycle

Ch31Describe the main functions of the ETL Manager, Warehouse Manager, Query Manager, and Metadata Repository.
  • ETL Manager: Performs all extraction, transformation, and loading of data into the warehouse. Extraction = copies from source systems. Transformation = cleans, standardises, creates surrogate keys. Loading = applies constraints as data enters DW.
  • Warehouse Manager: Manages data INSIDE the warehouse. Functions: consistency analysis, merging source data, creating indexes/views, generating denormalizations and aggregations, archiving and backing up data.
  • Query Manager: Manages user queries. Functions: directing queries to appropriate tables, scheduling execution of queries. May generate query profiles.
  • Metadata Repository: Stores "data about data." Three uses: (1) ETL — maps source fields to warehouse; (2) Warehouse management — automates aggregation; (3) Query management — directs queries to correct source. Major challenge: synchronising metadata across different vendor tools.

Reasons to implement:

  • Snowflake schema: Fact table in center surrounded by normalised dimension tables (dimensions can have sub-dimensions). Reduces storage redundancy but requires more joins — can hurt performance.

Ch32Discuss the four-step process for creating a dimensional model (Phase I of Kimball's BDL).

Ch32What are slowly changing dimensions? Describe Types 1, 2, and 3.

SCDs arise when "constant" dimensions (Branch, Staff, Client) actually change slowly over time. The DW must decide how to handle old vs new values.

  • Type 1 (Overwrite): New value simply replaces old value. No history. Simple but loses historical accuracy.
  • Type 2 (New Record): A new dimension record is created when the value changes. Old record preserved. Full history maintained. Most commonly used in data warehousing.
  • Type 3 (Alternate Attribute): A new column is added to the dimension table to hold both old and new values simultaneously in the same record. Limited history — only one prior value tracked.
Ch32Identify and discuss the purpose of surrogate keys in dimensional modeling.

A surrogate key is a simple integer key assigned in the DW to replace the natural key from the OLTP source system.

Why use surrogate keys?

  • Gives DW independence from OLTP systems — if OLTP changes its natural keys (e.g., branchNo format changes), the DW is unaffected
  • Simple integers → more efficient joins and indexing
  • Supports SCD Type 2 — multiple surrogate keys can exist for the same natural key (representing different time periods)
  • Provides a single consistent key even when data comes from multiple source systems with different key formats

Chapter 33 Questions

Ch33🔥 HotDescribe the five multidimensional operations available in OLAP.
  • Roll-Up: Aggregates data by moving UP the dimensional hierarchy (e.g., city → region) OR by reducing dimensions (4D → 3D). Results in less detail, higher aggregation.
  • Drill-Down: Reverse of roll-up. Reveals detailed data. Moves DOWN the hierarchy (region → city → area) OR by adding a dimension (3D → 4D). Results in more detail.
  • Slice: Selection on ONE dimension of the cube. Creates a 2D "slice." Example: show all revenue where type = 'Flat'.
  • Dice: Selection on TWO OR MORE dimensions. Creates a sub-cube. Example: revenue where type='Flat' AND time='Q1'.
  • Pivot: Rotates the data to provide an alternative view. Changes axis orientation without changing data. Example: swap location (x) with time (y) axes.
Ch33🔥 HotDescribe the four categories of OLAP servers.
  • MOLAP (Multidimensional OLAP): Uses specialised multidimensional database (MDDBMS) and array technology. Data preaggregated. Excellent performance for specific applications. Limited data volume; requires specialised skills.
  • ROLAP (Relational OLAP): Uses existing RDBMS + metadata layer. Creates multidimensional views from 2D relations. Fastest growing. Issues: complex query performance; needs middleware.
  • HOLAP (Hybrid OLAP): Combines ROLAP and MOLAP. Delivers subsets of data from DBMS or MOLAP server to desktop as cube. Issues: data redundancy; consistency problems across users.
  • DOLAP (Desktop OLAP): Stores OLAP data in client-based files. Client machine holds small data extracts and runs multidimensional engine locally. Issues: security; thin-client trend makes this harder to manage.
Ch33State and briefly explain Codd's 12 rules for OLAP tools.
  1. Multidimensional conceptual view — model must match users' multidimensional enterprise view
  2. Transparency — underlying technology invisible to users
  3. Accessibility — access data from all heterogeneous sources
  4. Consistent reporting performance — no degradation as dimensions/aggregations increase
  5. Client-server architecture — efficient in client-server environment
  6. Generic dimensionality — all dimensions equal in structure and capability
  7. Dynamic sparse matrix handling — efficient storage of empty cube cells (nulls)
  8. Multi-user support — concurrent users on same or different models
  9. Unrestricted cross-dimensional operations — auto roll-up within and across dimensions
  10. Intuitive data manipulation — point-and-click, drag-and-drop on cube cells
  11. Flexible reporting — any arrangement of rows, columns, cells
  12. Unlimited dimensions and aggregation levels — no artificial restrictions
Ch33Explain the ROLLUP and CUBE extensions to SQL. How many aggregation levels does each produce?

Both extend GROUP BY to produce multiple levels of aggregation in a single query.

ROLLUP:

  • Produces subtotals rolling up from most detailed to grand total, following column list order
  • With n columns → produces n+1 levels of aggregation
  • Example: ROLLUP(propertyType, yearMonth, city) with n=3 → 4 levels
  • Best for natural hierarchies (year → month → day)

CUBE:

  • Generates ALL possible combinations of subtotals for a data cube
  • With n columns → produces 2n combinations
  • Example: CUBE(propertyType, yearMonth, city) with n=3 → 8 combinations
  • Best for cross-tabular reports with independent dimensions
  • Includes everything ROLLUP produces PLUS additional combinations (e.g., city totals across property types)
Ch33What is the difference between RANK() and DENSE_RANK() in SQL OLAP extensions?

Both rank records based on measure values. The difference appears when there are ties:

  • RANK(): Leaves gaps in the sequence. If three records tie for 2nd place, next rank is 5th (2nd, 2nd, 2nd, 5th).
  • DENSE_RANK(): No gaps. If three records tie for 2nd place, next rank is 3rd (2nd, 2nd, 2nd, 3rd).

Syntax: RANK() OVER (ORDER BY columnList)

Ch33What is the relationship between OLAP and data warehousing?
  • A data warehouse stores large volumes of historical data.
  • OLAP tools sit ON TOP of the data warehouse and provide multidimensional analytical access to that data.
  • Together: DW + OLAP + Data Mining = Business Intelligence (BI) technologies.
  • OLAP goes beyond general query tools — it answers "why?" questions, not just "what?" and "who?" questions.
  • Data warehouse must be organised appropriately (star schema) to enable high-performance OLAP queries.
  • Real-time DW poses a challenge for OLAP — OLAP tools assume data is static; changing data during a query creates problems.

BatiniWhat are structural conflicts? Name and explain the four types.

Database Schema Integration

A Comparative Analysis of Methodologies for Database Schema Integration — the theoretical foundation for the "Integrated" property in Inmon's SITN definition.

⚠️ Why This Paper Matters for Your Midterm

Khalid Saleem assigned this to give the DW integration problem a formal theoretical grounding. Ch 31 says a DW must be "integrated" — this paper explains how that integration is done methodologically. Focus on: the definition of schema integration, causes of schema diversity, the 4 integration activities, types of conflicts, and goals of the integrated schema.

What is Schema Integration?

Schema Integration The activity of integrating the schemas of existing or proposed databases into a global, unified schema.

It occurs in two contexts:

  • View Integration (in database design): Produces a global conceptual description of a proposed database. Multiple designers/user groups produce their own schemas independently, then these are merged during conceptual design.
  • Database Integration (in distributed databases): Produces the global schema of a collection of existing databases. The global schema is a virtual view of all databases taken together in a distributed database environment.

⚡ The Core Motivation

One of the fundamental principles of the database approach is that a database allows a nonredundant, unified representation of all data managed in an organisation. This is only achievable when methodologies exist to support integration across organisational and application boundaries. This is precisely what the "Integrated" property in Inmon's SITN definition demands of a data warehouse.

Why Schema Integration Is Needed

Two reasons integration is necessary:

  • The structure of a database for large organisations is too complex to be modelled by a single designer in a single view.
  • User groups typically operate independently and have their own requirements and expectations of data — which may conflict with other user groups.

The preferred phase to perform integration is conceptual design — after requirements analysis but before implementation design. Doing it too early (requirements phase) is difficult because requirements are unstructured. Doing it too late (implementation phase) loses the power of abstraction.

1.2 Causes of Schema Diversity

Why do schemas from different designers/user groups differ? Three root causes:

1. Different Perspectives

Different user groups adopt their own viewpoints when modelling the same real-world objects. Example: one schema models Employee → Department directly; another schema models it via Employee → Project → Department. Same reality, different representations.

2. Equivalence Among Constructs

Multiple combinations of modelling constructs can represent the same domain equivalently. Example: "Publisher" modelled as an attribute of Book in one schema, but as a separate entity with a relationship in another. Both are valid — but incompatible for merging without transformation.

3. Incompatible Design Specifications

Erroneous choices regarding names, types, integrity constraints. Example: one schema shows Employee assigned to exactly one project (cardinality 1:n), while the correct schema allows many projects (n:m). A good integration methodology must detect such errors.

1.2.4 Semantic Relationships Between Representations

When the same concept appears in two schemas as representations R₁ and R₂, they can be:

RelationshipMeaning
IdenticalR₁ and R₂ are exactly the same — same constructs, same perceptions, no incoherence
EquivalentNot exactly the same because different but equivalent constructs were applied — same perception, coherent
CompatibleNeither identical nor equivalent — but not contradictory either
IncompatibleContradictory due to incoherence in specification — these are conflicts

Situations (2), (3), and (4) can all be interpreted as conflicts. A conflict = any situation that gives rise to R₁ and R₂ not being identical. Conflicts and their resolutions are central to the problems of integration.

1.3 The Four Steps of Schema Integration

Every integration methodology — regardless of its specific approach — can be understood as a combination of these four activities:

1

Preintegration

Analysis of schemas before integration to decide on integration policy: which schemas to integrate, in what order, what preferences to assign to schemas or portions of schemas. Global strategies are also decided here — how much designer interaction is needed, how many schemas to integrate at once. Collection of additional information (constraints, assertions among views) also happens here.

2

Comparison of Schemas

Schemas are analysed and compared to determine correspondences among concepts and detect possible conflicts. Two types of conflicts: naming conflicts and structural conflicts. Interschema properties may also be discovered during this step.

3

Conforming the Schemas

Once conflicts are detected, an effort is made to resolve them so that merging becomes possible. Automatic conflict resolution is generally not feasible — close interaction with designers and users is required. Schema transformations are the key mechanism: renaming, type transformations, restructuring.

4

Merging and Restructuring

Schemas are superimposed (merged) to produce an intermediate integrated schema. The result is then restructured to achieve the three qualitative goals: completeness, minimality, and understandability.

2.6 Types of Conflicts (Comparison Step)

Naming Conflicts

Homonyms

The same name is used for two different concepts in different schemas. Example: "Equipment" means computers in Schema 1 but furniture in Schema 2. Merging without detection would create a single entity for two distinct real-world objects.

Synonyms

The same concept is described by two different names. Example: "Client" in Schema 1 and "Customer" in Schema 2 refer to the same real-world concept. Keeping both in the integrated schema would model one object with two entities.

Structural Conflicts

Conflicts arising from different choices of modelling constructs or integrity constraints:

TypeDefinitionExample
Type ConflictsSame concept represented by different modelling constructs in different schemas"Publisher" is an attribute in Schema 1 but an entity in Schema 2
Dependency ConflictsSame group of concepts related by different dependencies in different schemasMarriage is 1:1 in one schema (one spouse) but m:n in another (marriage history)
Key ConflictsDifferent keys assigned to the same concept in different schemasEmployee identified by SS# in Schema 1 but by EmpID in Schema 2
Behavioral ConflictsDifferent insertion/deletion policies for the same class of objectsIn Schema 1 a department can exist without employees; in Schema 2 deleting the last employee deletes the department

2.7 Conforming — Schema Transformations

To resolve conflicts, schema transformations are applied. The goal is to reach a common canonical representation so that schemas can be merged. Examples:

  • Renaming: Resolves naming conflicts — unify "Topics" and "Keyword" into a single name
  • Type transformations: Transform an attribute into an entity (or vice versa) to reach structural compatibility
  • Restructuring: Simplify representation after merging

Important: no methodology surveyed provides a formal proof that its set of transformations is complete — i.e., capable of resolving any possible conflict.

2.8 Goals of the Integrated Schema (Merging & Restructuring)

After merging, the integrated schema is tested against three qualitative criteria:

Completeness & Correctness

The integrated schema must contain all concepts present in any component schema, correctly. It must represent the union of all application domains of the component schemas.

Minimality

If the same concept appears in more than one component schema, it must appear only once in the integrated schema. Redundant relationships, derived attributes, and cycles are identified and eliminated.

Understandability

The integrated schema should be easy to understand for both the designer and end user. Among all possible equivalent representations, the most understandable one should be chosen.

Integration Processing Strategies

Methodologies differ in how many schemas they integrate at one time:

StrategyHow it worksAdvantage
Binary — LadderIntegrate two schemas at a time; each step takes a new component schema and merges it with the current intermediate resultResolves conflicts in favour of the growing integrated schema; simpler at each step
Binary — BalancedSchemas divided into pairs at the start; integrated symmetricallyMinimises number of comparisons among concepts
N-ary — One-shotAll n schemas integrated in a single stepMinimises number of integration steps; allows full semantic analysis before merging
N-ary — IterativeGroups of schemas integrated iterativelyMost general; intermediate results refined progressively

Most methodologies prefer binary strategies because the merging algorithm complexity is n² in the number of schemas — keeping n=2 at each step reduces complexity significantly.

  • ETL Transformation step = practical implementation of Batini's conforming and merging stages. Standardising gender codes, date formats, field names during ETL = resolving naming and type conflicts.

The Influence of the Conceptual Model

Batini observes a fundamental trade-off in choosing a data model for integration:

  • Simpler model (e.g., relational): fewer type conflicts possible, simpler transformations, easier merging. But a weaker tool for discovering similarities and incompatibilities.
  • Richer semantic model (e.g., ER model): more powerful for representing predefined groupings and comparing at a higher level of abstraction. But more complex to work with. Deals with a much wider spectrum of conflicts.

The ER model and its variants dominate in practice — it is the most widely used model for schema integration and forms the basis of Batini & Lenzerini's own 1984 methodology.

Interschema Properties

During comparison and merging, hidden relationships between concepts in different schemas are discovered — these are called interschema properties. Example: Person in Schema 1 and Employee in Schema 2 have a subset relationship (all employees are persons) that was not visible in either component schema alone.

The most common interschema property used across methodologies is subsetting — the basis for accommodating multiple user perspectives on comparable classes of objects.

Data Preparation & Schema Matching

Erroneous values, missing values, outliers, univariate analysis, feature reduction, schema matching — Khalid's actual lecture slides.

Erroneous Values

Even when data is in standard form, it cannot be assumed to be error-free. Erroneous values arise due to: measurement errors, subjective judgments, malfunctioning or misuse of automatic recording equipment.

⚡ Two Categories (Slide W06-A)

  • Possible values of the attribute — valid for the dataset but incorrectly recorded (noisy values)
  • Not possible values — clearly invalid, fails format/range check (invalid values)

Noisy Values

Noisy Value

A value that is valid for the dataset but is incorrectly recorded. Example: 69.72 accidentally entered as 6.972. Or the colour brown accidentally recorded as blue. Noise is a perpetual problem — the value looks plausible so automated format checks miss it.

Invalid Values

Noisy values that are also invalid for the dataset — fail a format or range check. Examples: 69.7X (letter in numeric field), bbrown (extra character). Can be easily detected and corrected/rejected.

Cleaning Data — Sorting Approach

Hard to spot errors buried in 100,000 values. Sorting values into ascending order can reveal:

What You ObserveWhat It Means / What to Do
Variable takes only 6 distinct values, widely separatedTreat as categorical, not continuous
All values identical"Ignore" attribute — no analytical value
All values identical except oneDecide: error or genuinely significant?
Values outside normal range (e.g., 22654.8 when range is 200–5000)Investigate: data entry error or equipment malfunction
One value abnormally frequent ("Albania" in 10% of country fields)Likely default value problem — first list option auto-selected
Age = 72 in many records of a student surveyDefault DOB (01/01/1930) converted to age by poorly designed program

Outliers

Outlier

A genuine value significantly different from all others. NOT necessarily an error. Recognition of outliers may be the key to major discoveries — especially in medicine, physics, financial fraud. Do NOT blindly discard or adjust them.

Missing Values — Two Types

  • Attribute not applicable: e.g., certain medical data only meaningful for female patients. Best approach: split dataset into two parts and treat separately.
  • Attribute should be recorded but isn't: Equipment malfunction, form fields added after data collection started, information that could not be obtained.

Two Strategies for Missing Values

Strategy 1 — Discard Instances

Delete ALL instances with at least one missing value. Use the remainder.

Advantage: Conservative — no artificial errors introduced.
Disadvantage: Discarding data damages reliability. NOT recommended in general. Useless when most instances have missing values.

Use when: Missing proportion is small.

Strategy 2 — Replace by Estimate

Estimate each missing value using values that ARE present.

Categorical attributes: Most frequent non-missing value.
Continuous attributes: Average (mean) value.

Less cautious. May introduce noise. Use when missing proportion is large. Caution: if attribute is genuinely inapplicable for some instances, replacement gives invalid results.

Key point from slide: There is no single method better than all others for all datasets. Experiment with multiple strategies.

Feature / Dimension Reduction

Feature Reduction / Dimension Reduction

Reducing the number of attributes before processing a dataset. Modern storage is cheap so organisations record everything — but too many irrelevant attributes add computational overhead and cause data mining algorithms to perform poorly.

Example from slide: 10,000 attributes per supermarket customer. Goal: predict who will buy cat food. Only 5–10 attributes matter. At best, irrelevant attributes add overhead. At worst, they cause poor predictions.

Schema Matching (Slide W07)

Schema Matching

Takes two schemas/ontologies as input and produces a mapping between elements of the two schemas that correspond semantically to each other.

1-1 Match

One element in Source A maps to exactly one element in Source B.
Example: price ↔ listed-price

Complex Match

One element maps to a combination of elements.
Example: author-name ↔ a-fname + a-lname

Schema matching applies to: Distributed Databases, Data Warehousing, Data Mining, Information Retrieval, Knowledge Extraction, and Mediation systems.

  • Level 2: GROUP BY Country + Region (subtotal: all cities within each region)
  • Level 3: GROUP BY Country (subtotal: all regions within each country)
  • Level 4: GROUP BY nothing (grand total: everything)

ROLLUP drops columns from the RIGHT side first at each level.

⚠️ CUBE vs ROLLUP — Critical Difference

  • ROLLUP only rolls up in one direction (left to right through columns). It would give (Cat,Reg,Yr), (Cat,Reg), (Cat), () — that's it
  • CUBE gives ALL combinations. The blue rows above — (Region+Year), (Region), (Year) — are CUBE ONLY. ROLLUP would never produce them
  • This matters for lab task "Create dimensions (time, product, location), query the cube for insights" — CUBE gives you all cross-dimensional totals

ROLLUP vs CUBE — Formula Summary

ROLLUP(A, B, C)  →  n = 3  →  n+1 = 4 aggregation levels
CUBE(A, B, C)    →  n = 3  →  2³  = 8 combinations

USE ROLLUP when: dimensions have natural hierarchy (Country→Region→City)
USE CUBE when:   dimensions are independent (Category × Region × Year)

CUBE always produces MORE rows than ROLLUP for same column set.

⚡ RANK vs DENSE_RANK — Memorise This

  • RANK(): Leaves gaps after ties. Two tied at 2nd → next is 4th. Like Olympic/sports rankings.
  • DENSE_RANK(): No gaps. Two tied at 2nd → next is 3rd. Dense continuous sequence.
  • Syntax: RANK() OVER (ORDER BY column DESC) — ORDER BY determines direction

Advanced SQL: Window Functions — Moving Averages

-- Monthly sales for Punjab with 3-month moving average
SELECT
    YEAR(Date)  AS Year,
    MONTH(Date) AS Month,
    SUM(Sales_Amount) AS Monthly_Sales,

    -- Moving average: current month + 2 preceding months
    AVG(SUM(Sales_Amount)) OVER (
        ORDER BY YEAR(Date), MONTH(Date)
        ROWS 2 PRECEDING
    ) AS Moving_Avg_3Month,

    -- Running total: first month to current month
    SUM(SUM(Sales_Amount)) OVER (
        ORDER BY YEAR(Date), MONTH(Date)
        ROWS UNBOUNDED PRECEDING
    ) AS Running_Total

FROM dbo.sales_dataset
WHERE Region = 'Punjab'
GROUP BY YEAR(Date), MONTH(Date)
ORDER BY YEAR(Date), MONTH(Date);

⚡ How ROWS 2 PRECEDING Works

  • Month 1: window = [Month 1] → average of 1 value
  • Month 2: window = [Month 1, Month 2] → average of 2 values
  • Month 3+: window = [current-2, current-1, current] → average of 3 values
  • ROWS UNBOUNDED PRECEDING = from very first row to current row = cumulative/running total

Apache Spark & Databricks — What You Need to Know

Apache Spark

A distributed computing framework for processing large-scale datasets across multiple machines (nodes) in parallel. Dramatically faster than traditional single-machine databases for big data workloads.

Databricks

A cloud-based platform built on Apache Spark. Provides a notebook interface (like Jupyter) to write and run Spark SQL queries. Managed Spark — you don't set up the cluster yourself.

⚡ Key Facts for the Exam

  • Khalid introduced Databricks as a platform to run SQL at scale — same SQL syntax works (ROLLUP, CUBE, RANK, window functions)
  • Databricks processes data in parallel across a cluster — this is why it handles massive datasets
  • In Databricks: load CSV → create DataFrame → register as table → run SQL on it
  • The conceptual understanding of ROLLUP, CUBE, RANK etc. is exactly the same whether you're in SQL Server, Databricks, or any other SQL system
