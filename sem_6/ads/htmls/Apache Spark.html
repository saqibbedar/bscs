Section 01

Vertical vs Horizontal Scaling

Before Spark even enters the picture, you need to understand why distributed computing exists. It comes down to one question: when your data grows beyond what one machine can handle, what do you do?

① Vertical Scaling (Monolithic Approach)
Buy a bigger, more powerful single machine. More RAM, faster CPU, larger disk — all in one box. The application itself doesn't change; you just throw better hardware at it.

Problem: There is a physical ceiling. The world's most powerful single server still cannot process petabytes of live data. And if that one machine dies, everything dies — zero fault tolerance. Also called the monolithic approach because the entire system is one unit.
② Horizontal Scaling
Add more machines to the cluster. Data and computation are distributed across all nodes. When one node dies, only its slice of work is affected — other nodes continue. The cluster reroutes or retries.

Advantage: Near-unlimited scalability. Commodity hardware. True fault tolerance — dying of one node wouldn't lose data (your instructor's exact words).
Figure 1 — Vertical scaling hits a physical ceiling and is a single point of failure. Horizontal scaling distributes work across commodity machines; one failure doesn't kill the cluster.
Section 02

Hadoop MapReduce → Apache Spark

The Problem with Hadoop MapReduce

Hadoop MapReduce was the first major horizontal scaling solution for big data. It worked, but it had a fundamental architectural flaw: after every Map and Reduce step, it wrote intermediate results to disk (HDFS). Disk I/O is orders of magnitude slower than memory access.

Figure 2 — Hadoop MapReduce's fatal flaw: every intermediate step forces a disk write to HDFS and a disk read back. Disk is ~100× slower than RAM.

Apache Spark's Solution: In-Memory Processing

Spark keeps intermediate data in RAM across operations. It doesn't write to disk between steps unless memory runs out (spill). This is why Spark is 100× faster than Hadoop for iterative workloads — the data just stays in memory, operations chain together without touching disk.

Disk sequential read speed ≈ 100–200 MB/s
RAM read speed ≈ 10,000–50,000 MB/s
Ratio ≈ 50–500× faster in memory → "100× faster" is the conservative practical number
Section 03

Spark Architecture: Driver · Cluster Manager · Workers

Spark follows a master-slave architecture. One Driver node coordinates; many Worker nodes execute. A Cluster Manager sits between them handling resource allocation.

Figure 3 — Full Spark cluster architecture (from official docs + lab notes). Orange dashed = task dispatch. Green dashed = result return. Blue = resource negotiation.

Component Responsibilities (unambiguous breakdown)

Driver Node
The brain. Runs your Spark application code (main function). Creates SparkContext. Converts logical plan → DAG → tasks. Talks to Cluster Manager for resources. Coordinates all executors. Collects final results. It is a JVM process.
Cluster Manager
The landlord. Doesn't know about Spark jobs specifically — just manages CPU/RAM across the cluster. Spark supports: Standalone (built-in), YARN (Hadoop's resource manager), Kubernetes, Apache Mesos. After resources are allocated, Cluster Manager steps back.
Worker Node / Executor
The muscles. Runs actual computation tasks. Each worker node has one or more Executor JVM processes. Each Executor has task threads (parallel workers) and a cache in RAM. Registers with Driver. Sends heartbeats. Returns results.

Why Databricks Came

Your instructor's exact words: "Databricks came because it hard-coded the code required to make nodes as in Apache Spark. After all lists are passed, resource manager goes away and Driver node becomes master. Then orchestration tools (YARN or Kubernetes) are used to take orders."

Let's unpack this precisely:

The Problem Databricks Solved
Setting up Apache Spark from scratch requires: configuring the cluster, installing Spark on every node, configuring YARN or Kubernetes, writing cluster bootstrap scripts, managing node provisioning, handling Spark version compatibility, configuring networking between nodes... This is enormous infrastructure work before you write a single line of data processing code. Every organization was repeating the same cluster setup boilerplate.
What Databricks Did
The founders of Apache Spark (from UC Berkeley AMPLab) built Databricks to abstract away all cluster management. You get a managed Spark environment — just write your DataFrame code. The platform handles: node provisioning, Spark installation, YARN/Kubernetes orchestration, autoscaling, job scheduling, and monitoring. The "hard-coded" part your instructor mentioned = Databricks internally runs all the Spark cluster wiring automatically, no manual configuration.
Figure 4 — Spark job lifecycle. Resource Manager launches the Application Master Container (AMC) which contains the Driver. Once executors are allocated, the Resource Manager steps back and the Driver directly orchestrates all work.
Section 05

Deep Dive: Driver Node & the Py4J Bridge

Spark is written in Scala/Java and runs on the JVM. Python is not a JVM language. So when you write PySpark code, how does it actually run? This is the Py4J bridge — one of the most important internal mechanisms in Spark.

Figure 5 — The Py4J bridge (from lab notes). PySpark runs as a Python process on the Driver. Py4J translates Python API calls into Java object calls on the Spark JVM. The JVM compiles tasks and sends JVM bytecode to workers — not Python.

Why Workers Cannot Run Python Directly

Critical Point from your notes
Your instructor noted: "PySpark main interprets the PySpark code; it can't interpret Python in worker nodes, so there is an optional interpreter to convert Py to Java. Java is used in the backend of many systems."

The worker executors are pure JVM processes. They have no Python interpreter. When you write df.filter(...) in PySpark, the Python call goes through Py4J to the Spark JVM on the Driver, which compiles it into a logical plan and ultimately into JVM bytecode tasks. These bytecode tasks — not Python — are shipped to executors.
Exception: UDFs (User Defined Functions)
If you write a Python UDF (udf(lambda x: x*2)), Spark cannot compile that to JVM bytecode automatically. It must launch a Python subprocess on the worker, serialize data from JVM → Python via pickle, run your function, and serialize results back. This is why Python UDFs are dramatically slower than native Spark operations. This is the "optional interpreter" your instructor mentioned.
# This goes through Py4J → JVM → compiled plan → workers: FAST df.filter(df.city == "Lahore").groupBy("dept").count() # This launches Python subprocess on EACH worker: SLOW from pyspark.sql.functions import udf my_udf = udf(lambda x: x.upper()) # Python UDF → runs in Python on worker df.withColumn("upper_city", my_udf(df.city))
Section 06

Lazy Evaluation & RDD

Lazy Evaluation

Spark does not execute transformations the moment you write them. It builds up a DAG (Directed Acyclic Graph) of all pending operations and only executes when you trigger an action.

Transformations (lazy — build the plan)
.filter(), .select(), .map(), .groupBy(), .join(), .withColumn()

Nothing happens. Spark just records what you want to do.
Actions (trigger — execute everything)
.show(), .collect(), .count(), .write(), .save()

NOW Spark optimizes the full DAG and executes it across the cluster.
Why lazy evaluation exists
By seeing the full pipeline before executing, Spark's Catalyst Optimizer can: eliminate redundant operations, push filters down (read less data), reorder joins, combine steps into fewer shuffle operations. If Spark executed eagerly (like Pandas), it couldn't see the big picture to optimize. This is a central reason Spark is fast.

RDD — Resilient Distributed Dataset

RDD (Resilient Distributed Dataset)
The fundamental, immutable, distributed data abstraction in Spark. A logical partition of data spread across nodes, with a lineage graph (DAG) that records every transformation applied to it, enabling automatic recomputation if a partition is lost.

Three key properties of an RDD, all encoded in the name:

R — Resilient
If a partition is lost (node dies), Spark re-derives it by replaying the transformation lineage from the source. No data is permanently lost.
D — Distributed
Partitions of the RDD live on different nodes. Operations run in parallel across all partitions simultaneously.
D — Dataset
A collection of records. Can be key-value pairs, rows, objects — any typed collection.
RDD vs DataFrame
DataFrames (and Datasets) are built on top of RDDs. When you write df.filter(...), Spark ultimately converts it to RDD operations under the hood. DataFrames add a schema (typed columns) and go through the Catalyst Optimizer — that's why they're faster than raw RDDs for structured data. Your lab focused on DataFrames, but RDD is the foundation everything rests on.
Section 07

Narrow vs Wide Transformations

This distinction determines whether Spark needs to shuffle data across the network or can process it locally. Shuffle is expensive — it's the main performance bottleneck in Spark jobs.

Narrow Transformation
A transformation where each output partition depends on at most one input partition. No data movement across nodes required. Each worker can independently process its partition.
Wide Transformation (Shuffle)
A transformation where each output partition may depend on multiple input partitions from different nodes. Requires a shuffle — data is physically moved across the network to co-locate records that need to be combined.
Figure 6 — Narrow vs Wide transformations. Narrow: 1-to-1 partition dependency, no network I/O. Wide: many-to-many, requires shuffle — data physically moves between nodes over the network. This is the stage boundary in Spark's DAG.

Section 08 ★ Exam Core

Joins in Spark — All 3 Strategies

When you join two DataFrames in Spark, the engine must decide how to physically execute the join. There are 3 strategies. Spark's Catalyst Optimizer picks automatically, but understanding them is essential for performance tuning.

The core problem
To join df1 and df2 on a key (e.g. staffNo), rows with the same key must be on the same machine. If staffNo=42 is on Worker 1 in df1 but on Worker 3 in df2, the join cannot happen locally. Data must be moved. The 3 strategies differ in how they solve this movement problem.

① Shuffle Sort Merge Join (SMJ)

Shuffle Sort Merge Join
Both DataFrames are shuffled so that rows with the same key end up on the same partition. Within each partition, rows are sorted by key. Then a merge operation scans both sorted partitions simultaneously to find matching rows.
Figure 7 — Shuffle Sort Merge Join. Both sides shuffled by hash(key), sorted within partitions, then merged. O(N log N) per partition due to sort step. Your instructor noted: "Check start — can't ask in clauses" → meaning SMJ doesn't support non-equi joins (you can't use <, > in the join condition).

② Shuffle Hash Join (SHJ)

Shuffle Hash Join
Both DataFrames are shuffled so same-key rows co-locate. Instead of sorting, Spark builds a hash table from the smaller partition in memory, then probes it with rows from the larger partition. Same hash = same partition (your instructor's exact phrasing).
Figure 8 — Shuffle Hash Join. Shuffle ensures same-key rows co-locate. Hash table built from smaller partition, probed with larger. O(1) per row vs O(N log N) for sort — faster when data fits in memory.

③ Broadcast Join

Broadcast Join
When one DataFrame is small enough to fit in each executor's memory, Spark broadcasts a full copy of it to every worker node. Each worker then performs the join locally against its own partition of the large DataFrame — no shuffle at all.
Figure 9 — Broadcast Join. Small table copied to every worker; large table stays in place. No shuffle of the large DF. Fastest join strategy. Default threshold = 10MB.
Section 09

Query Plan Pipeline — Catalyst Optimizer

When you write df.filter(...).groupBy(...).agg(...), Spark doesn't execute it directly. It passes it through a 4-stage optimization pipeline called the Catalyst Optimizer. This is what your instructor drew on the board.

Figure 10 — Catalyst Optimizer pipeline (from board diagram in notes). Code → Unresolved Logical Plan → (Analysis) → Resolved Logical Plan → (Catalyst Rules) → Optimized Logical Plan → (Cost Models) → Physical Plan selection → Execution.

What the Catalyst Optimizer Actually Does

Predicate Pushdown
Filter as early as possible — read less data from disk. df.join(df2).filter(x > 5) becomes df.filter(x > 5).join(df2).
Column Pruning
Only read columns actually needed. SELECT id, name FROM ... → only those 2 columns touched, not the entire row.
Constant Folding
Evaluate constant expressions at compile time. WHERE 2 + 2 = 4 → WHERE TRUE, no runtime cost.
Join Reordering
Put smaller tables earlier in join chains. Reduce data volume for subsequent operations.
Section 10

Driver Memory Management

The Driver node has its own JVM with a specific memory layout. Your instructor gave exact numbers.

Figure 11 — Driver memory. Your instructor's numbers: 1 GB heap + 10% overhead. Actual overhead uses max(384 MB, 10%) — so for 1 GB, overhead is 384 MB (not 100 MB), giving 1.384 GB total container. The "1.05 GB" in notes assumed ~50 MB overhead; the correct formula gives 1.384 GB at minimum.
Instructor's numbers vs exact formula
Your notes say "1 GB + 100 MB = 1.05 GB, overhead = 10%". The 10% of 1 GB = 100 MB is right, BUT the actual Spark formula is max(384 MB, 10% × memory). For 1 GB driver, 10% = 100 MB, which is less than 384 MB, so overhead = 384 MB, total = 1.384 GB. Your instructor gave the 10% rule correctly; the 384 MB minimum is the full formula from Spark's source code.
Section 11

Worker / Executor Memory — JVM Heap Breakdown

This is the most mathematically precise section. Every number your instructor gave has a formula behind it. Let's derive everything from first principles.

Worker Memory — 4 Components (from notes)

① JVM Heap Memory
The main Spark memory (spark.executor.memory). Default: 1 GB. This is where all Spark operations happen.
② Off-Heap Memory
Memory outside JVM, managed by OS directly. No garbage collection overhead. Default = 0 (disabled). Enable with spark.memory.offHeap.enabled=true.
③ Overhead Memory
Same formula as driver: max(384 MB, 10% × executor memory). For JVM internal use, thread stacks, GC metadata.
④ PySpark Main Memory
Memory for the Python process on the worker (when Python UDFs run). Default = 0. Separate from JVM heap.

Inside the JVM Heap — 3 Regions

Figure 12 — JVM Heap breakdown (from lab notes + official Spark docs). Three regions with exact formulas. Note the flexible boundary between Storage and Execution — execution can borrow from storage (evicting cached data), but storage cannot evict active execution memory.
Let E = spark.executor.memory
Reserved = 300 MB (hardcoded)
Remaining = E − 300 MB
Spark Pool = 0.6 × (E − 300 MB)
User Memory = 0.4 × (E − 300 MB)
Check: 300 + Spark Pool + User Memory = E ✓

Within Spark Pool:
Storage Memory (initial) = 0.5 × Spark Pool (spark.memory.storageFraction)
Execution Memory (initial) = 0.5 × Spark Pool (but can grow by borrowing from Storage)
Section 12

Worker Memory Out-of-Order: Spill & Salting

Spill-over Effect

When a Spark task's data exceeds available executor memory, Spark spills the excess to disk. This is not a crash — it's a graceful degradation. But it causes a massive performance hit because disk I/O is brought back into the picture (the thing Spark was designed to avoid).

Figure 13 — Spill-over effect. When a task's data exceeds executor memory, overflow is written to local disk (spill files). The serialization + disk I/O + deserialization cycle kills performance. Spark logs: "SpillableIterator: Spilling data to disk".

Salting — Fix for Data Skew

Data skew = one key has far more rows than others. Example: 90% of your orders are from one city. One executor gets 90% of the data → memory explodes → spill → slow job.

Salting
Artificially adding a random suffix to the join/group key to distribute the data more evenly across partitions. The key is split into N sub-keys, processed in parallel, then results are combined. Your instructor mentioned ÷ 4 — meaning you split into 4 salt buckets.
Figure 14 — Salting with divisor 4. The hot key "LHR" is split into LHR_0, LHR_1, LHR_2, LHR_3 using a random suffix (row_number % 4). Each gets ~22,500 rows instead of one partition getting all 90,000. After aggregation, sub-results are combined. No partition overflows.
# Salting implementation in PySpark from pyspark.sql.functions import rand, floor, concat, col, lit SALT_FACTOR = 4 # your instructor's ÷ 4 # Add salt column to the skewed DataFrame df_salted = df.withColumn("salted_key", concat(col("city"), lit("_"), (floor(rand() * SALT_FACTOR)).cast("string")) ) # GroupBy on salted key (distributes the work) df_partial = df_salted.groupBy("salted_key").agg(count("*").alias("partial_count")) # Extract original key and sum partial results df_result = df_partial \ .withColumn("city", split(col("salted_key"), "_").getItem(0)) \ .groupBy("city").agg(sum("partial_count").alias("total_count"))
Section 13

Partition Pruning

Your instructor drew a directory tree with ISB.csv, LHR.csv, KCh.csv and showed that a filtered query only reads the relevant files. This is partition pruning.

Partition Pruning
When data is physically organized into folders by a column value (partitioned storage), Spark's query planner reads only the directories that match the filter predicate, skipping all others. No I/O is wasted on irrelevant partitions.
Figure 15 — Partition pruning from lab notes. Files are physically organized by city column. Query WHERE city IN ('ISB','LHR') → Spark's planner reads only city=ISB/ and city=LHR/ directories, skipping KCh/ and all others entirely.
# Write data partitioned by city — enables partition pruning on reads df.write.partitionBy("city").parquet("/data/flights/") # Creates: /data/flights/city=ISB/part-0.parquet # /data/flights/city=LHR/part-0.parquet # /data/flights/city=KCh/part-0.parquet # Now this query reads ONLY city=ISB/ and city=LHR/ — KCh never touched spark.read.parquet("/data/flights/") \ .filter(col("city").isin("ISB", "LHR")) \ .show()
Section 14

Adaptive Query Execution (AQE)

AQE is Spark's runtime optimization system, introduced in Spark 3.0. Your instructor summarized it as "optimization techniques." Here is the precise mechanism:

Adaptive Query Execution (AQE)
A runtime optimization framework that re-optimizes query plans mid-execution based on actual runtime statistics collected after each shuffle stage, rather than relying solely on pre-execution estimates.
Why it exists
The Catalyst Optimizer (Section 9) makes decisions before execution based on table statistics that may be stale or inaccurate. AQE waits until a shuffle stage completes, reads the actual partition sizes produced, and re-plans the rest of the query with ground-truth data. It's "plan as you go" rather than "plan everything upfront."

AQE's 3 Main Optimization Techniques

① Coalesce Small Partitions
After a shuffle, if 200 output partitions exist but most are tiny (e.g., 100 KB each), AQE merges them into fewer, larger partitions. Avoids the overhead of 200 task launches for tiny data.
② Dynamic Join Strategy Switching
If Catalyst planned a Shuffle Sort Merge Join but at runtime one side turns out to be small enough (<10 MB), AQE switches to Broadcast Join — without re-running the whole query.
③ Skew Join Optimization
Detects skewed partitions at runtime (one partition much larger than others) and automatically splits the hot partition — similar to manual salting, but done automatically by the engine.
Figure 16 — AQE re-optimization cycle. After every shuffle stage completes, AQE reads actual partition statistics and re-plans the next stage. The original query plan becomes a living document that improves as execution proceeds.
AQE vs Manual Optimization
Before AQE, developers manually tuned spark.sql.shuffle.partitions, manually broadcast tables, and manually implemented salting for skew. AQE automates all three of these. It's the most significant performance improvement in Spark 3.x. Enabled by default since Spark 3.2.
