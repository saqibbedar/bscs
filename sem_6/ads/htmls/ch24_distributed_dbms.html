Section 24.1

Introduction & Core Concepts p. 785–788

Previously, we focused on centralized database systems — a single logical database at one site under one DBMS. Now we enter distributed territory: data physically spread across machines connected by a network, yet appearing as a single unified system to users.

Distributed Database
A logically interrelated collection of shared data (and a description of this data) physically distributed over a computer network. p. 787
Distributed DBMS (DDBMS)
The software system that permits the management of the distributed database and makes the distribution transparent to users. p. 787

The Key Characteristics of a DDBMS p. 787

  • Data is split into a number of fragments
  • Fragments may be replicated (copied at multiple sites)
  • Fragments/replicas are allocated to sites
  • Sites are linked by a communications network
  • Each site has its own local DBMS
  • Each local DBMS can handle local applications autonomously
  • Each DBMS participates in at least one global application
Figure 24.1 (p. 788) — A DDBMS: 4 sites connected via a computer network, each holding a fragment of the distributed database. Users at any site can access data at any other site transparently.

DDBMS vs Distributed Processing — a critical distinction p. 788

Distributed Processing
A centralized database that can be accessed over a network. Data is still in one place — only access is distributed.
Key Point
In a true DDBMS, data is physically distributed across sites. In distributed processing, data is centralized but users access it from multiple locations. The DDBMS is NOT just remote access to one DB.

Parallel DBMSs — also distinct p. 789–791

A parallel DBMS links multiple processors/machines to improve performance, usually within the same physical site. Three architectures:

Shared Memory
Multiple processors share one memory pool. Fast but limited to ~64 processors before bottleneck.
Shared Disk
Each processor has private memory but can access all disks. Eliminates memory bottleneck. Also called clusters.
Shared Nothing (MPP)
Each processor has its own memory AND disk. Most scalable. Data partitioned across disks. Performance best when data is local.
Parallel vs Distributed
Parallel DBMS nodes are typically at the same site with fast interconnects. DDBMS nodes are geographically distributed, separately administered, with slower network links.
Section 24.1.2

Advantages & Disadvantages p. 791–794

✓ Advantages
  • Reflects org structure — data lives where it's used (e.g. DreamHome branches)
  • Improved shareability — local data can be accessed globally
  • Improved availability — one site failing doesn't kill the system
  • Improved reliability — replicated data survives node failures
  • Better performance — data near users, parallel processing
  • Economics — cheaper to add workstations than upgrade mainframes
  • Modular growth — add new sites without disrupting existing ones
  • Integration — legacy systems can coexist
✗ Disadvantages
  • Complexity — much harder to manage than centralized
  • Cost — higher procurement, maintenance, network costs
  • Security — network adds attack surface; replicated data harder to control
  • Integrity control harder — enforcing constraints across sites is expensive
  • Lack of standards — no universal protocols yet
  • Lack of experience — less industry knowledge than centralized systems
  • Design more complex — fragmentation + allocation + replication = hard
Section 24.1.3

Homogeneous vs Heterogeneous DDBMSs p. 794–797

Homogeneous DDBMS
All sites run the same DBMS product. Easier to design and manage. Allows incremental growth. Can exploit parallelism easily.

Example: 5 branches, all running SQL Server 2022
Heterogeneous DDBMS
Sites run different DBMS products, possibly different data models (relational, network, hierarchical). Requires translation between systems. Usually results from independent legacy systems being integrated later.

Example: Branch A on Oracle, Branch B on MySQL, Branch C on old COBOL flat files

Multidatabase Systems (MDBS) p. 796

Multidatabase System (MDBS)
A distributed DBMS in which each site maintains complete autonomy — local DBMSs are not modified, an additional software layer sits on top.

An MDBS sits transparently on top of existing databases, presenting a single view to users. It maintains a global schema while local DBMSs maintain all user data. Two types exist:

4 Components of a DDBMS p. 804

Standard DBMS at each site controlling local data. Has its own local system catalog.

Section 24.4.1

Distributed DB Design: Data Allocation p. 805–808

The three core problems in distributed DB design are Fragmentation, Allocation, and Replication. We first look at the four allocation strategies.

Design Objectives p. 806

Locality of Reference
Store data near where it's used most.
Reliability & Availability
Replication ensures another copy exists if one site fails.
Acceptable Performance
Avoid bottlenecks from bad placement decisions.
Minimal Communication Costs
Minimize data sent across the network.
Balanced Storage Costs
Use cheap mass storage where possible.

Four Allocation Strategies p. 806–807

Strategy Locality Reliability Performance Storage Cost Comm. Cost
Centralized
One DB, one site		 Lowest Lowest Unsatisfactory Lowest Highest
Fragmented
Disjoint, one copy each		 High* Low/item, High/system Satisfactory* Lowest Low*
Complete Replication
Full copy at every site		 Highest Highest Best for reads Highest High for updates
Selective Replication
Mix of all 3 — most common		 High* Low/item, High/system Satisfactory* Average Low*

* Subject to good design

Takeaway
Selective replication is the most commonly used strategy because it combines the advantages of all others without the worst disadvantages of any single approach.
Section 24.4.2

Fragmentation — All 4 Types p. 807–815

Why Fragment? p. 807–808

Usage
Apps work with views (subsets), not whole relations — so distribute subsets.
Efficiency
Store data close to where it's used; don't store what's not needed locally.
Parallelism
Subqueries on fragments can run concurrently at different sites.
Security
Data not needed at a site isn't stored there — reduces exposure.

3 Rules of Correct Fragmentation p. 808

  • 1
    Completeness — Every data item in relation R must appear in at least one fragment. No data loss.
  • 2
    Reconstruction — It must be possible to reconstruct the original relation R from its fragments using relational operations.
  • 3
    Disjointness — A data item in fragment Rᵢ should not appear in any other fragment. (Exception: vertical fragmentation must repeat the primary key for reconstruction.)
Figure 24.8 / 24.9 (p. 809) — Overview of fragmentation types. Horizontal splits rows; Vertical splits columns (keeping PK); Mixed combines both.

1. Horizontal Fragmentation p. 809–811

Horizontal Fragment
Consists of a subset of the tuples (rows) of a relation. Defined using the Selection operation: σp(R) where p is a predicate.
Example 24.2 — DreamHome PropertyForRent (p. 810)

Split PropertyForRent by property type (only 'House' or 'Flat' exist):

P1: σtype='House'(PropertyForRent) P2: σtype='Flat'(PropertyForRent)

Correctness check:

  • Completeness: Every property appears in P1 or P2 ✓
  • Reconstruction: P1 ∪ P2 = PropertyForRent ✓
  • Disjointness: No property is both 'House' and 'Flat' ✓

2. Vertical Fragmentation p. 811–812

Vertical Fragment
Consists of a subset of the attributes (columns) of a relation. Defined using the Projection operation: Πa1,...,an(R). Primary key must appear in every fragment.
Example 24.3 — DreamHome Staff table (p. 811)

Payroll dept needs: staffNo, position, sex, DOB, salary. HR dept needs: staffNo, fName, lName, branchNo.

Key point
staffNo appears in BOTH fragments — this violates disjointness but is necessary for reconstruction. The book explicitly notes this is the exception rule for vertical fragmentation.

3. Mixed (Hybrid) Fragmentation p. 812–813

Mixed Fragment
A horizontal fragment that is then vertically fragmented, or a vertical fragment that is then horizontally fragmented. Uses both Selection and Projection operations.
Example 24.4 — Continuing from Example 24.3 (p. 813)

Take S2 (HR fragment) and horizontally fragment it by branch:

S21: σbranchNo='B003'(S2) S22: σbranchNo='B005'(S2) S23: σbranchNo='B007'(S2)

Reconstruction: S1 ⋈ (S21 ∪ S22 ∪ S23) = Staff

Each branch office only holds the HR data for its own staff. S1 (payroll) stays at one central payroll site.

4. Derived Horizontal Fragmentation p. 814–815

Derived Fragment
A horizontal fragment of a child relation based on the horizontal fragmentation of a parent relation. Uses the Semijoin operation. Defined as: Rᵢ = R ⋉f Sᵢ
Example 24.5 — Staff and PropertyForRent (p. 814)

Staff is fragmented by branchNo (S3, S4, S5). To keep related properties with their managing staff, we derive PropertyForRent fragments:

-- Staff fragments (parent): S3: σbranchNo='B003'(Staff) → Site 3 S4: σbranchNo='B005'(Staff) → Site 4 S5: σbranchNo='B007'(Staff) → Site 5 -- PropertyForRent derived fragments (child): Pi = PropertyForRent ⋉staffNo Si (for i = 3, 4, 5)

P3 = all properties managed by B003 staff, stored at Site 3. Join between Staff and PropertyForRent can now be performed locally at each site — no expensive cross-site joins needed.

Why Derived Fragmentation Matters
Applications that frequently join Staff and PropertyForRent benefit enormously — both child and parent fragments co-locate at the same site, making the join local (fast) rather than distributed (slow and expensive).
Section 24.5

Transparencies in a DDBMS p. 816–824

The fundamental principle: "To the user, a distributed system should look exactly like a non-distributed system." Transparency is how we achieve this.

1. Distribution Transparency p. 816–819

Three levels, ordered from highest (most hidden) to lowest (least hidden):

Transparency Levels (p. 816–818) — Three levels of distribution transparency. Higher = simpler for users but harder to implement for the DDBMS.

The Same Query at Three Levels p. 817–818

Recall the mixed fragmentation: S1 at Site 5, S21 at Site 3, S22 at Site 5, S23 at Site 7. Query: "Get names of all Managers."

-- ① Fragmentation Transparency (user writes normal SQL): SELECT fName, lName FROM Staff WHERE position = 'Manager';
-- ② Location Transparency (user knows fragments, not locations): SELECT fName, lName FROM S21 WHERE staffNo IN (SELECT staffNo FROM S1 WHERE position='Manager') UNION SELECT fName, lName FROM S22 WHERE staffNo IN (SELECT staffNo FROM S1 WHERE position='Manager') UNION SELECT fName, lName FROM S23 WHERE staffNo IN (SELECT staffNo FROM S1 WHERE position='Manager');
-- ③ Local Mapping Transparency (user specifies site numbers too): SELECT fName, lName FROM S21 AT SITE 3 WHERE staffNo IN (SELECT staffNo FROM S1 AT SITE 5 WHERE position='Manager') UNION ... (continues for each fragment/site)
Why this matters for your quiz
The teacher's hint about "nested queries across fragments" corresponds exactly to Location Transparency — the user must name fragments and use nested subqueries (UNION + WHERE staffNo IN ...) because data is split across multiple sites. This is the SQL pattern to know.

2. Transaction Transparency p. 819–821

Ensures all distributed transactions maintain the database's integrity and consistency. A distributed transaction is divided into subtransactions, one per site, each represented by an agent.

Concurrency Transparency
Results of concurrent distributed transactions must be logically consistent with serial execution. More complex than centralized — global AND local transactions must not interfere.
Failure Transparency
Must handle: loss of a message, communication link failure, site failure, network partitioning. Global transaction must be fully committed or fully rolled back (ACID atomicity).

DRDA Transaction Classification p. 821

Remote Request
One SQL statement sent to a remote site. Executes and references data only at that site.
Remote Unit of Work
Multiple SQL statements (one transaction) sent to one remote site. Local site controls commit/rollback.
Distributed Unit of Work
Transaction's SQL statements go to different sites, but each statement uses data from only one site.
Distributed Request
Most complex. One SQL statement may join/union data from multiple sites simultaneously.

3. Performance Transparency p. 822

The DDBMS should perform as if it were centralized. The Distributed Query Processor (DQP) must consider: which fragment to access, which replica to use, and which location to use — optimizing against communication cost, I/O cost, and CPU cost.

4. DBMS Transparency p. 824

Hides the fact that local DBMSs may be different (heterogeneous). The hardest transparency to provide.

Section 24.5.3

Distributed Query Processing — Response Times p. 822–824

This is one of the most important sections. The DQP must choose the right strategy — the wrong choice can mean the difference between 1 second and 2.3 days.

Communication Time Formula (p. 800)
Time = C₀ + (bits_in_message / transmission_rate)
where C₀ = access delay (fixed cost per message). Small messages sent one-by-one are catastrophically slow because of repeated C₀.
Example 24.7 — DreamHome query across London and Glasgow (p. 823)

Three tables: Property (10,000 rows, London), Client (100,000 rows, Glasgow), Viewing (1,000,000 rows, London).
Transmission rate: 10,000 chars/sec. Access delay C₀ = 1 second per message.

Query: Properties in Aberdeen viewed by clients with maxPrice > £200,000.

StrategyApproachTime
1Move Client (100k rows) to London, process there16.7 minutes
2Move Property + Viewing (1M rows) to Glasgow28 hours
3Check Glasgow for each of 100k Aberdeen viewings2.3 days
4Get 10 matching clients from Glasgow, check London for each20 seconds
5Join at London, project result, move to Glasgow16.7 minutes
6Select 10 clients at Glasgow, move result to London ✓1 second
The lesson
Strategy 6 wins because it transfers only 10 rows (the small filtered set), not the entire large table. Filter first, transfer the smallest result set. Strategy 3 is catastrophic because it sends 100,000 individual messages — each with a 1-second access delay.
Section 24.6

Date's Twelve Rules for a DDBMS p. 825–826

Fundamental Principle
"To the user, a distributed system should look exactly like a non-distributed system."
1
Local autonomy — each site controls its own data and local operations
2
No central site reliance — no single point of failure; no central server
3
Continuous operation — no planned shutdowns to add/remove sites
4
Location independence — user can access any data as if it's local
5
Fragmentation independence — user unaware of how data is fragmented
6
Replication independence — user unaware of copies; can't address a specific copy
7
Distributed query processing — queries referencing multiple sites work
8
Distributed transaction processing — ACID properties hold globally
9
Hardware independence — run on any hardware
10
OS independence — run on any operating system
11
Network independence — run on any communication network
12
Database independence — support heterogeneous local DBMSs
Note
Rules 9–12 are ideals. No current system fully complies with all 12. The last 4 are especially hard because of the lack of universal hardware, OS, and DBMS standards.
