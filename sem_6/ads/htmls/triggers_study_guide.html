Section 01

What is a Trigger?

A trigger (something that causes an action automatically) is a special type of stored procedure (a saved block of SQL code in the database) that runs automatically when a specific event happens on a table.

🔑 Core Idea
You don't call a trigger manually. You do something to a table (INSERT / UPDATE / DELETE), and the trigger fires on its own — like a motion sensor light. Someone walks in → light turns on. You insert a row → trigger fires.

Why do we use triggers?

Your notes mention three key uses:

① Data Validation (checking that data is correct)

Use a BEFORE trigger to check and fix data before it enters the table. Example: salary cannot be negative → change it to 0 automatically.

② Audit Logging (keeping a record of who did what)

Use an AFTER trigger to write a record into a log table every time an employee is inserted, updated, or deleted.

③ Organizational Constraints (business rules of a company)

Rules that go beyond simple CHECK constraints — e.g., if the department is "HR", ensure salary is within a specific range.

④ Auto-calculated Values

Automatically compute and insert derived values. Example: when inserting a sale row, automatically update the total_sales column.

📝 From Your Notes
"Triggers in physical memory — better performance than CHECK."

Triggers are stored in physical (disk-based, persistent = stays even after restart) memory of MySQL, so once defined they are always available without re-running code.
Section 02

Two Types of Triggers

Your notes show exactly two types. This is about how many times the trigger fires:

1. Row-Level Trigger

Fires once for every row affected by the SQL statement.

Example: If you insert 50 rows in one statement, this trigger fires 50 times.

Keyword: FOR EACH ROW

2. Statement-Level Trigger

Fires once per SQL statement, regardless of how many rows it affects.

Example: If you insert 50 rows in one statement, this trigger fires only 1 time.

(NOT available in MySQL — only in PostgreSQL)

⚠️ MySQL Specific — Important for Your Quiz
MySQL supports ONLY row-level triggers (FOR EACH ROW). Statement-level triggers exist in PostgreSQL (another database system) — both DDL and DML triggers are available there. Your lab uses MySQL, so everything you write will always have FOR EACH ROW.
📌 Also from notes: DML vs DDL
Triggers in MySQL are DML (Data Manipulation Language — INSERT, UPDATE, DELETE) triggers only. For DDL (Data Definition Language — CREATE, DROP, ALTER) → no triggers in MySQL. PostgreSQL supports both.
Section 03

The 6 Row-Level Trigger Types

From your notes: "Row Level Triggers — 6 types". These come from combining timing (BEFORE / AFTER) × event (INSERT / UPDATE / DELETE):

INSERT
BEFORE INSERT
Validate/modify data before it's saved. e.g. fix negative salary → 0
UPDATE
BEFORE UPDATE
Check new value before it's applied. e.g. reject negative salary updates
DELETE
BEFORE DELETE
Log the record or cancel deletion if needed. Access OLD data.
INSERT
AFTER INSERT
Log that a new record was added. e.g. write to employee_log
UPDATE
AFTER UPDATE
Log what changed. e.g. record old salary → new salary
DELETE
AFTER DELETE
Confirm deletion in log. OLD data is still accessible.
Simple Memory Rule
BEFORE = intercept and change data before it hits the table → use for validation (checking if data is correct)
AFTER = react to something that already happened → use for audit logs (records of changes for accountability)

Section 04

NEW and OLD Keywords

Inside a trigger body, you can access two special row references: NEW and OLD. Think of them as the row "before the operation" and "after the operation."

Keyword What it refers to Available in INSERT? Available in UPDATE? Available in DELETE?
NEW The row as it will be written to the table (the incoming data) ✔ YES ✔ YES ✘ NO
OLD The row as it existed before this operation ✘ NO ✔ YES ✔ YES
Logic behind this:
INSERT: There is no "old" row — you're creating a brand new one. Only NEW exists.
DELETE: You're removing the row. There's nothing "new" being inserted. Only OLD exists.
UPDATE: You have both — the old version and the new version. Use OLD.salary for what it was, NEW.salary for what it will become.
⚡ Key difference: BEFORE vs AFTER with NEW
In a BEFORE trigger, you can actually modify NEW.column before it's saved. This is how the BEFORE INSERT trigger in the lab changes a negative salary to 0 — it sets SET NEW.salary = 0. In an AFTER trigger, the row is already saved — modifying NEW has no effect.

From your notes:

"NEW — generally used with BEFORE. For newly inserted rows."
"OLD — old rows which are already there, can be accessed."

More precisely: NEW is available in both BEFORE and AFTER, but it's useful to modify only in BEFORE.
Section 05

The DELIMITER — Why We Need It

MySQL uses a semicolon ; as the statement terminator (the character that tells MySQL "this statement is complete, execute it"). Inside a trigger body, you also use semicolons to separate SQL statements. This creates a problem: MySQL would try to execute the trigger halfway through when it hits the first inner semicolon.

The solution is to temporarily change the delimiter to something else — usually // — while creating the trigger, then change it back to ; afterward.

DELIMITER // ← "From now on, // means END of statement, not ;"

CREATE TRIGGER my_trigger
BEFORE INSERT ON employees FOR EACH ROW
BEGIN
    IF NEW.salary < 0 THEN
        SET NEW.salary = 0; ← this ; does NOT confuse MySQL now
    END IF;
END// ← THIS is the actual end of the CREATE TRIGGER statement

DELIMITER ; ← "Okay, go back to ; as the terminator"
From your notes:
"By default MySQL uses ; so it gets confused — so we use the delimiter."

Exactly right. The DELIMITER command is a MySQL client instruction, not actual SQL. It just tells MySQL Workbench / command line: "treat // as the end of a statement for now."

Full Trigger Syntax Breakdown

DELIMITER // Temporarily change the statement terminator to //
CREATE TRIGGER trigger_name Give the trigger a unique name
BEFORE | AFTER TIMING — when should this fire?
INSERT | UPDATE | DELETE EVENT — which operation triggers it?
ON table_name Which table to watch
FOR EACH ROW Row-level trigger (mandatory in MySQL)
BEGIN Start of the trigger body
    -- your SQL logic here Can use NEW.column, OLD.column, IF-THEN, INSERT, etc.
END// End of body — // is the statement terminator here
DELIMITER ; Restore normal ; terminator
Section 07

Lab Walkthrough — All 6 Triggers Explained

The lab creates an emp_db database with two tables and 6 triggers. Let's go through each one.

The Two Tables

employees table Main Data Table 
CREATE TABLE employees (
    emp_id     INT PRIMARY KEY AUTO_INCREMENT,  -- unique ID, auto-assigned
    emp_name   VARCHAR(100),                      -- employee's name
    salary     DECIMAL(10,2),                     -- salary, 2 decimal places
    department VARCHAR(50)                        -- department name
);
employee_log table Audit Log Table 
CREATE TABLE employee_log (
    log_id      INT PRIMARY KEY AUTO_INCREMENT,
    action_type VARCHAR(50),              -- what happened: "AFTER INSERT", etc.
    emp_id      INT,                       -- which employee this log entry is about
    action_time TIMESTAMP DEFAULT CURRENT_TIMESTAMP, -- automatically records when
    message     VARCHAR(255)               -- human-readable description
);

Trigger 1 — BEFORE INSERT

Purpose
Intercept an INSERT before it happens. If the salary being inserted is negative (invalid), change it to 0.
before_employee_insert BEFORE INSERT 
CREATE TRIGGER before_employee_insert
BEFORE INSERT ON employees
FOR EACH ROW
BEGIN
    IF NEW.salary < 0 THEN
        SET NEW.salary = 0;   -- modify the incoming data
    END IF;
END//
NEW.salary = the salary value the user tried to insert. We check if it's < 0 and overwrite it with 0. The table then receives 0, not the negative value — the user never even gets an error message.

Trigger 2 — AFTER INSERT

Purpose
After a new employee is successfully added, write a log entry saying who was inserted.
after_employee_insert AFTER INSERT 
CREATE TRIGGER after_employee_insert
AFTER INSERT ON employees
FOR EACH ROW
BEGIN
    INSERT INTO employee_log(action_type, emp_id, message)
    VALUES ('AFTER INSERT', NEW.emp_id,
            CONCAT('Employee ', NEW.emp_name, ' inserted'));
END//
CONCAT() joins strings together. So if we insert 'Ali', the message becomes: "Employee Ali inserted". NEW.emp_id is the auto-assigned ID of the newly inserted row.

Trigger 3 — BEFORE UPDATE

Purpose
Before a salary update, check if the new salary is negative. If yes, keep the old salary instead.
before_employee_update BEFORE UPDATE 
CREATE TRIGGER before_employee_update
BEFORE UPDATE ON employees
FOR EACH ROW
BEGIN
    IF NEW.salary < 0 THEN
        SET NEW.salary = OLD.salary;  -- reject the change, restore old value
    END IF;
END//
Notice: here both OLD and NEW are used. NEW.salary is what the user tried to set. OLD.salary is what it was before. By setting NEW.salary = OLD.salary, we effectively cancel (undo) the bad update.

Trigger 4 — AFTER UPDATE

Purpose
After a salary is updated, log the change — show what the old value was and what the new value is.
after_employee_update AFTER UPDATE 
CREATE TRIGGER after_employee_update
AFTER UPDATE ON employees
FOR EACH ROW
BEGIN
    INSERT INTO employee_log(action_type, emp_id, message)
    VALUES ('AFTER UPDATE', NEW.emp_id,
            CONCAT('Salary updated from ',
                   OLD.salary, ' to ', NEW.salary));
END//
Example message produced: "Salary updated from 50000.00 to 60000.00". This is a classic audit trail (a record of all changes, for accountability).

Trigger 5 — BEFORE DELETE

Purpose
Before deleting an employee, log the fact that we are about to delete them. This preserves a record of who existed before they're removed.
before_employee_delete BEFORE DELETE 
CREATE TRIGGER before_employee_delete
BEFORE DELETE ON employees
FOR EACH ROW
BEGIN
    INSERT INTO employee_log(action_type, emp_id, message)
    VALUES ('BEFORE DELETE', OLD.emp_id,
            CONCAT('Deleting employee ', OLD.emp_name));
END//
Only OLD is used here — there is no NEW in a DELETE trigger. The row is being removed, so no "new" version of it exists.

Trigger 6 — AFTER DELETE

Purpose
After the deletion is complete, write a confirmation log entry.
after_employee_delete AFTER DELETE 
CREATE TRIGGER after_employee_delete
AFTER DELETE ON employees
FOR EACH ROW
BEGIN
    INSERT INTO employee_log(action_type, emp_id, message)
    VALUES ('AFTER DELETE', OLD.emp_id,
            CONCAT('Employee ', OLD.emp_name, ' deleted'));
END//
Even in an AFTER DELETE trigger, OLD is still accessible — MySQL keeps it available within the scope of the trigger execution even though the row is already removed from the table.
Checking All Triggers: SHOW TRIGGERS
SHOW TRIGGERS FROM emp_db;
This lists all 6 triggers with their table, event, timing, and body.

Section 09

⚡ Quiz Prep — Expected Questions & Answers

Q1: What is a trigger in MySQL?
A trigger is a type of stored procedure that automatically executes when a specific DML event (INSERT, UPDATE, or DELETE) occurs on a table. It does not need to be called manually.
Q2: What are the two types of triggers based on level?
Row-level trigger: fires once for every row affected (uses FOR EACH ROW). Statement-level trigger: fires once per SQL statement. MySQL only supports row-level triggers.
Q3: What is the difference between BEFORE and AFTER triggers?
A BEFORE trigger fires before the DML operation executes — it can modify the NEW row data. An AFTER trigger fires after the operation is complete — used for logging/auditing since the change is already committed.
Q4: What is NEW and OLD in a trigger?
NEW refers to the row being inserted or the new version of a row being updated. OLD refers to the row before it was updated or deleted. In INSERT triggers: only NEW. In DELETE triggers: only OLD. In UPDATE triggers: both are available.
Q5: Why do we use DELIMITER // in MySQL triggers?
MySQL uses semicolons (;) as statement terminators. Since trigger bodies also contain semicolons, MySQL would misinterpret them. By changing the delimiter to //, we tell MySQL to treat // as the end of the full CREATE TRIGGER statement, then restore ; afterward.
Q6: In the lab, what happens when you INSERT salary = -10000?
The BEFORE INSERT trigger fires. It checks if NEW.salary < 0 — true, so it sets NEW.salary = 0. The row is then inserted with salary = 0.00, not -10000. The AFTER INSERT trigger then logs the insertion.
Q7: What is the purpose of the employee_log table in the lab?
It serves as an audit log — a permanent record of all database operations (insertions, updates, deletions). Every AFTER trigger in the lab writes a row into this table with the action type, employee ID, timestamp, and a message describing what happened.
Q8: How many triggers fire when you DELETE one row from employees?
Two triggers fire: the BEFORE DELETE trigger (logs 'Deleting employee X') and the AFTER DELETE trigger (logs 'Employee X deleted'). So 2 log entries are created per deletion.
Q9: How would you view all triggers in a database?
SHOW TRIGGERS FROM emp_db; — this lists all triggers with their event, table, timing, and body.
Q10: Can triggers be used for DDL operations (CREATE, DROP) in MySQL?
No. In MySQL, triggers only work with DML operations (INSERT, UPDATE, DELETE). DDL triggers are not supported in MySQL, though PostgreSQL supports both DDL and DML triggers.
🎯 Key Vocabulary to Know for the Quiz
  • Trigger — automated stored procedure that fires on DML events
  • Stored Procedure — pre-written block of SQL saved in the database
  • DML (Data Manipulation Language) — INSERT, UPDATE, DELETE
  • DDL (Data Definition Language) — CREATE, DROP, ALTER
  • Audit log — record of database changes for accountability
  • Data validation — checking and enforcing correct data before saving
  • FOR EACH ROW — the keyword making it a row-level trigger
  • NEW / OLD — special row references inside trigger bodies
  • DELIMITER — MySQL client instruction to change statement terminator
  • CONCAT() — MySQL function to join strings together
