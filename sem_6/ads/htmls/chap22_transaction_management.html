Section 01

ACID Properties

Every transaction must satisfy four properties. These are the most fundamental and most tested concept in this chapter.

A
Atomicity

"All or nothing." A transaction either completes entirely or not at all. If it fails midway, everything it did is rolled back. Ensured by the recovery subsystem.

C
Consistency

A transaction takes the database from one consistent state to another. Integrity constraints must hold before and after. Ensured by DBMS + application developers.

I
Isolation

Transactions execute independently of each other. Partial results of an incomplete transaction are invisible to other transactions. Ensured by concurrency control.

D
Durability

Once committed, changes are permanent — even if the system crashes immediately after. Ensured by the recovery subsystem.

Quick: who ensures what?
Atomicity & Durability → Recovery Manager  |  Isolation → Concurrency Control  |  Consistency → Both DBMS and Application

Section 03

The 5 Concurrency Problems

When multiple transactions run simultaneously without control, these problems occur. Know all 5 — the first 3 are the most tested.

#Problem NameWhat happensFix
1
Lost Update
 T1 and T2 both read x (=100). T2 writes 200. T1 writes 90. T2's update is lost — overwritten by T1. Prevent T1 from reading x until T2 commits
2
Uncommitted Dependency
aka Dirty Read
 T1 reads a value written by T2, but T2 aborts. T1 has read data that never officially existed. The bad value is called dirty data. Prevent T1 reading x until T2 commits or aborts
3
Inconsistent Analysis
aka Unrepeatable Read
 T1 is summing balances (x, y, z). While it reads them, T2 updates some. T1 gets the wrong total — it read old values of some and new values of others. Prevent T2 from updating while T1 is reading
4
Nonrepeatable Read
aka Fuzzy Read
 T1 reads x, then reads it again. Between the two reads, T2 changed x. T1 gets two different values for the same item. Lock x for the duration of T1's transaction
5
Phantom Read
 T1 runs a query → gets rows R. T2 inserts a new row that matches T1's query. T1 runs the same query again → gets R + the new "phantom" row. Predicate locking (range locks)
Section 04

Serializability & Precedence Graphs

Serial Schedule
Transactions execute one after another — no interleaving. Always correct, but reduces concurrency.
Serializable Schedule
A concurrent (interleaved) schedule that produces the same result as some serial execution. Goal of concurrency control.

When do operations conflict?

Two operations conflict if they belong to different transactions, access the same data item, and at least one is a write.

T1 operationT2 operationSame item?Conflict?
ReadReadYes✓ NO — safe
ReadWriteYes✗ YES
WriteReadYes✗ YES
WriteWriteYes✗ YES
AnythingAnythingNo✓ NO — safe

Precedence (Serialization) Graph — Testing Conflict Serializability

How to draw a precedence graph
  1. Create one node per transaction
  2. Draw an edge Ti → Tj if Tj reads what Ti wrote
  3. Draw an edge Ti → Tj if Tj writes what Ti read
  4. Draw an edge Ti → Tj if Tj writes what Ti wrote
  5. If there is a cycle → NOT conflict serializable
  6. If no cycle → IS conflict serializable (serial order = topological sort)
Precedence Graph Example — 2 transactions

Recoverable Schedule

A schedule is recoverable if: whenever Tj reads data written by Ti, the commit of Ti happens before the commit of Tj. This prevents a situation where Tj has committed based on data that Ti then rolls back.
Section 05

Locking

Locking is the most widely used approach to concurrency control. Before accessing a data item, a transaction must acquire a lock on it.

S Lock Shared Lock
Transaction can read the item but not update it.
Multiple transactions can hold a Shared lock on the same item simultaneously.
X Lock Exclusive Lock
Transaction can read AND update the item.
Only one transaction can hold an Exclusive lock — no other lock is allowed.

Lock Compatibility Table

Holds S lock Holds X lock No lock
Request S ✓ Grant ✗ Wait ✓ Grant
Request X ✗ Wait ✗ Wait ✓ Grant
Lock granularity
A lock can be placed at different levels: entire database → file → page → record → field. Finer granularity = more concurrency but more overhead. Coarser granularity = less overhead but less concurrency.
Section 06

Two-Phase Locking (2PL)

Basic locking alone doesn't guarantee serializability. The Two-Phase Locking protocol does — it's the most important concurrency technique in this chapter.

2PL Rule
A transaction follows 2PL if all locking operations precede the first unlock operation. Once it releases any lock, it can never acquire a new one.

📈 Phase 1: Growing Phase

  • Transaction acquires locks
  • Cannot release any lock
  • Lock upgrades (S→X) allowed here

📉 Phase 2: Shrinking Phase

  • Transaction releases locks
  • Cannot acquire new locks
  • Lock downgrades (X→S) allowed here
Guarantee
If every transaction follows 2PL, the schedule is guaranteed to be conflict serializable.

Variants of 2PL

VariantWhat it doesWhy
Basic 2PL Release locks any time during shrinking phase Can cause cascading rollbacks
Strict 2PL Hold exclusive (X) locks until transaction commits or aborts Prevents dirty reads; avoids cascading rollbacks
Rigorous 2PL Hold all locks (S and X) until commit or abort Strictest — transactions serialize in commit order. Used by most DBMSs.
Conservative 2PL Acquire all needed locks at start Prevents deadlock but impractical — must know all locks in advance

Cascading Rollback

Problem with Basic 2PL
If T1 writes x and releases the lock, T2 reads that x and commits — then T1 aborts, T2 must also be undone (it read dirty data), and anything T3 read from T2 too. One failure cascades into multiple rollbacks.
Fix: Use Strict or Rigorous 2PL — hold locks until commit, so no one can read uncommitted data.
Section 07

Deadlock

Definition
An impasse where two or more transactions are each waiting for locks held by the other. Neither can proceed. Classic example: T1 holds lock on X, wants Y. T2 holds lock on Y, wants X.

Three Approaches to Handling Deadlock

ApproachHow it works
Timeout Transaction waits only a specified time for a lock. If not granted → assume deadlock, abort and restart. Simple but may abort transactions that aren't actually deadlocked.
Deadlock Prevention
(Wait-Die / Wound-Wait)		 Use timestamps to order. Wait-Die: older transaction waits for younger; younger dies (aborts). Wound-Wait: older wounds (aborts) younger; younger waits for older.
Deadlock Detection + Recovery Let it happen. Periodically build a Wait-For Graph (WFG). If WFG has a cycle → deadlock exists. Abort the cheapest victim to break it.

Wait-For Graph (WFG) — Most Testable

How to build a WFG
  1. Create one node per transaction
  2. Draw edge Ti → Tj if Ti is waiting for a lock currently held by Tj
  3. Cycle in WFG = Deadlock
WFG Example — T17 and T18 deadlocked

Cycle detected → DEADLOCK! Abort one (e.g. T18) to break it.

Choosing the Deadlock Victim

Abort the transaction with minimum cost — consider: how long it's been running (shorter = abort first), how many changes it made (fewer = abort first), how many changes it still needs to make. Also avoid starvation — don't always pick the same victim (track abort count).

Livelock vs Deadlock
Deadlock: transactions are stuck waiting for each other — detected by WFG cycle.
Livelock: a transaction is permanently skipped in the lock queue — no cycle in WFG but it never gets the lock. Fix with a FIFO queue (first-come-first-served).
Section 08

Timestamping

Key Difference from Locking
No locks → no deadlock possible. Instead: each transaction gets a unique timestamp at start. Each data item stores read_timestamp and write_timestamp. Conflicts → rollback (not wait).

Basic Timestamp Ordering Rules

When transaction T issues READ(x):
  • If ts(T) < write_timestamp(x) → T is trying to read a value written by a younger transaction. Abort T, restart with new timestamp.
  • Otherwise → allow read. Set read_timestamp(x) = max(ts(T), read_timestamp(x))
When transaction T issues WRITE(x):
  • If ts(T) < read_timestamp(x) → a younger transaction already read the current value; we can't overwrite it. Abort T, restart.
  • If ts(T) < write_timestamp(x) → a younger transaction already wrote; T's write is obsolete. Abort T, restart (or ignore via Thomas's Write Rule).
  • Otherwise → allow write. Set write_timestamp(x) = ts(T)
Thomas's Write Rule (extension)
If ts(T) < write_timestamp(x) — instead of aborting, safely ignore the obsolete write (a younger transaction has already written a newer value). Allows more concurrency.
Section 09

Database Recovery

The Log File

The DBMS keeps a log (journal) — a sequential record of all database changes. It survives failures. Each record contains:

START Transaction identifier — "T1 has started"
WRITE Transaction ID, data item, before-image (old value), after-image (new value)
COMMIT Transaction ID — "T1 has committed successfully"
ABORT Transaction ID — "T1 has been aborted"
CHECKPOINT IDs of all active transactions at checkpoint time
Write-Ahead Log (WAL) Protocol
Log records must be written to disk before the actual database write. This guarantees we can always undo or redo — we never lose the record of what happened.

Checkpoints

What is a checkpoint?
A point of synchronization: the DBMS flushes all log records and modified buffer pages to disk, then writes a CHECKPOINT record to the log. On recovery, we only need to look back to the last checkpoint — not the entire log.

At a checkpoint, three things happen:

  1. All log records in memory → written to secondary storage
  2. All modified buffer blocks → written to secondary storage
  3. A checkpoint record (with active transaction IDs) → written to log

UNDO and REDO — The Core Recovery Logic

Recovery Timeline — crash at tf, checkpoint at tc
What's in the logAction on RecoveryWhy
START + COMMIT (committed before checkpoint) NOTHING Changes already written to disk at checkpoint
START + COMMIT (committed after checkpoint) REDO — reapply using after-images Committed but changes may not have reached disk
START only (no COMMIT in log) UNDO — reverse using before-images Transaction was active at crash — must be rolled back (Atomicity)

Recovery Techniques

Deferred Update (No-Steal)

  • Updates NOT written to database until after commit
  • On failure: only REDO needed — aborted transactions never wrote anything
  • Log records written to disk before commit
  • No UNDO required
  • Drawback: needs large buffers to hold uncommitted changes

Immediate Update (Steal)

  • Updates written to database as they happen
  • Log record written before database update (WAL)
  • On failure: need both UNDO (for uncommitted) and REDO (for committed but not yet on disk)
  • Most DBMSs use this (Steal, No-Force policy)

Shadow Paging (alternative)

Maintains two page tables: current and shadow. Shadow never changes during the transaction. On commit → current becomes shadow. On abort → discard current, shadow is still intact. No log needed — but causes fragmentation.

Section 10

⚡ Quiz Prep

Q1: What are the ACID properties and who ensures each?
Atomicity (all-or-nothing) → Recovery Manager
Consistency (valid state to valid state) → DBMS + Application Developers
Isolation (transactions independent) → Concurrency Control
Durability (committed = permanent) → Recovery Manager
Q2: What are the 3 main concurrency problems? Describe each briefly.
Lost Update: T1 and T2 both read x, T2 writes, T1 overwrites T2's change — T2's update is lost.
Dirty Read (Uncommitted Dependency): T1 reads data written by T2, but T2 aborts — T1 worked with data that never officially existed.
Inconsistent Analysis: T1 is summing values across multiple items while T2 is updating them — T1 gets a mix of old and new values, producing an incorrect total.
Q3: What is a serializable schedule? How do you test for conflict serializability?
A serializable schedule is a concurrent schedule that produces the same result as some serial execution. To test: draw a precedence graph — one node per transaction, add directed edge Ti→Tj for each conflict where Ti's operation precedes Tj's conflicting operation. If the graph has no cycle → conflict serializable. If it has a cycle → not.
Q4: What is the difference between a Shared lock and an Exclusive lock?
A Shared (S) lock allows the transaction to read but not update the item. Multiple transactions can hold S locks on the same item simultaneously. An Exclusive (X) lock allows both read and write — no other transaction can hold any lock (S or X) on the same item.
Q5: Explain 2PL and its two phases.
Two-Phase Locking requires that all lock acquisitions precede all releases. Phase 1 (Growing): acquire locks, no releases. Phase 2 (Shrinking): release locks, no acquisitions. 2PL guarantees conflict serializability. Strict 2PL holds X locks until commit. Rigorous 2PL holds all locks until commit.
Q6: What is cascading rollback and how does Rigorous 2PL prevent it?
Cascading rollback occurs when T1 aborts and T2 (which read T1's uncommitted data) must also abort, and T3 (which read T2's data) must also abort — one failure cascades into many. Rigorous 2PL prevents this by holding all locks until commit — no transaction can read uncommitted data because the lock is never released early.
Q7: What is a Wait-For Graph and how do you use it?
A WFG has one node per transaction. Draw edge Ti→Tj if Ti is waiting for a lock currently held by Tj. A cycle in the WFG means deadlock exists. To resolve: choose a victim transaction (minimum cost), abort it, release its locks. This breaks the cycle and allows other transactions to proceed.
Q8: What does a log file contain and why is the Write-Ahead Log important?
The log contains: transaction start, write records (transaction ID, item, before-image, after-image), commit records, abort records, and checkpoint records. The Write-Ahead Log (WAL) protocol requires log records to be written to disk before the database update. This ensures that if a crash occurs, the recovery manager can always undo or redo operations.
Q9: After a crash with a checkpoint at tc, which transactions do you UNDO and which do you REDO?
UNDO: transactions that were active (running) at the time of crash — no COMMIT record in log. Reverse using before-images.
REDO: transactions that committed after the last checkpoint — have a COMMIT record but changes may not have reached disk. Reapply using after-images.
Nothing: transactions that committed before the checkpoint — already safely on disk.
Q10: Deferred Update vs Immediate Update — key difference?
Deferred Update: writes delayed until after commit. Only REDO needed on recovery (no UNDO — nothing was ever written for aborted transactions).
Immediate Update: writes applied as they happen (WAL). Both UNDO and REDO needed on recovery. Used by most real DBMSs (Steal + No-Force policy).
