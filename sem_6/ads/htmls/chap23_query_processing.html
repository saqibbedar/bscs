Section 01

What is Query Processing?

Query processing is the set of activities that happens after you write an SQL query — parsing it, validating it, converting it to relational algebra, optimizing it, and executing it to get the data back.

Because SQL is declarative (you say what you want, not how to get it), the DBMS has to figure out the best way to actually retrieve the data. That decision-making process is query optimization.

⚡ Why does it matter? — Example 23.1
The query "Find all Managers who work at a London branch" can be run 3 ways:
  • Strategy 1: Cartesian product first → 101,050 disk accesses
  • Strategy 2: Join, then filter → 3,050 disk accesses
  • Strategy 3: Filter first, then join → 1,160 disk accesses
Strategy 3 is 87× faster than Strategy 1 — same result, same SQL.

Canonical form = SQL translated blindly (expensive). Optimized = push filters down early (cheap). The exam expects you to show both, and explain the transformation.
Section 04

Building the Canonical (Initial) RA Tree

When SQL is first converted to relational algebra, the DBMS produces a canonical relational algebra tree — the naive, direct translation. Here is exactly how to build it:

Rules for Building the Canonical Tree

  • 1
    Each table in FROM → a leaf node at the bottom FROM Staff, Branch → two leaf nodes: Staff and Branch
  • 2
    Multiple tables → connected by Cartesian product (×) nodes Staff × Branch sits above both leaf nodes
  • 3
    The WHERE clause → a single big Selection (σ) node above the Cartesian product All conditions (join + filter) go into one σ on top of ×
  • 4
    The SELECT clause → a Projection (π) node at the very root πs.staffNo, s.fName sits at the top
⚠️ Canonical form is always inefficient
Cartesian product creates n × m rows (e.g., 1000 × 50 = 50,000 rows) just to filter them afterward. The optimizer's job is to fix this by pushing selections down before the join happens.
Section 05

The 12 Transformation Rules

These rules let you legally rearrange a relational algebra expression without changing its result. They are the mathematical basis for optimization.

# Rule Name What it says Expression
1 Cascade of Selection One big σ with AND can be split into separate nested σs σp∧q∧r(R) = σp(σq(σr(R)))
2 Commutativity of σ Order of nested selections doesn't matter σp(σq(R)) = σq(σp(R))
3 Cascade of Projection Only the outermost projection matters πL(πM(πN(R))) = πL(R)
4 σ and π Commute If predicate only uses projected columns, swap σ and π πA1..Am(σp(R)) = σp(πA1..Am(R))
5 Commutativity of Join Join order doesn't change the result R ⋈p S = S ⋈p R
6 σ and Join Commute ⭐ If σ only involves one table, push it inside before the join σp(R ⋈ S) = σp(R) ⋈ S
(where p involves only R)
7 π and Join Commute Push projections past joins when attributes are split across tables πL1∪L2(R ⋈ S) = πL1(R) ⋈ πL2(S)
8 Commutativity of ∪ and ∩ Set union and intersection are commutative (but NOT set difference) R ∪ S = S ∪ R  |  R ∩ S = S ∩ R
9 σ and Set Ops Commute Push σ inside union/intersection/set difference σp(R ∪ S) = σp(R) ∪ σp(S)
10 π and Union Commute Push projection inside union πL(R ∪ S) = πL(R) ∪ πL(S)
11 Associativity of Join ⭐ Regroup joins to change which pair is computed first (R ⋈ S) ⋈ T = R ⋈ (S ⋈ T)
12 Associativity of ∪ and ∩ Set operations can be regrouped (R ∪ S) ∪ T = S ∪ (R ∪ T)
⭐ For the exam, Rules 1, 6, and 11 are the most important
Rule 1: Split AND conditions into separate σs so you can push them down individually.
Rule 6: Push σ that only involves one table down below the join → reduces the join's input.
Rule 11: Reorder joins so the smaller result is computed first.
Section 06

The 5 Heuristics — Your Optimization Checklist

These are the practical rules you apply to the canonical tree to get the optimized tree. Apply them in order for the exam.

  • H1
    Perform σ (Selection) as early as possible — push it DOWN the tree Use Rule 1 to split σp∧q into two σs. Then use Rule 6 to push each σ down as far as possible toward the leaf node whose table it references. This reduces the number of rows before any join happens. Keep predicates on the same relation together.
  • H2
    Replace σ + × (Cartesian product) with ⋈ (Join) If a Selection predicate is a join condition (e.g., Staff.branchNo = Branch.branchNo), and it sits above a Cartesian product, replace the whole thing with a single Join node. Joins are far cheaper than Cartesian products + subsequent filtering.
  • H3
    Use associativity of joins (Rule 11) to reorder — most restrictive join first If you have two consecutive joins, use Rule 11 to reorder so the join that produces the fewest rows happens first. This makes the second join work on a smaller relation. Ask: "which condition is most selective?" — that one goes first.
  • H4
    Perform π (Projection) as early as possible — push it DOWN the tree Use Rules 3 and 7 to push projections down past joins. Dropping unnecessary columns early reduces the size of intermediate results. Keep only the attributes needed for the final SELECT or for subsequent join conditions.
  • H5
    Compute common sub-expressions once and cache them If the same sub-expression appears more than once in the tree (common in views), compute it once and store the result in memory for reuse. Only worthwhile if the intermediate result is small enough to store cheaply.
🎯 Exam Shortcut — The Golden Rule
The single most important optimization is: filter (σ) before you join (⋈). This alone — moving the WHERE conditions inside, down to the leaf tables — produces the biggest speedup. Everything else is secondary.
Section 07

Worked Example — Full 3-Step Answer

This is based on Example 23.1 from your textbook — the DreamHome database. Staff table has 1000 tuples, Branch has 50. Query: Find all Managers who work at a London branch.

① Write the SQL (given)
SELECT *
FROM   Staff s, Branch b
WHERE  s.branchNo = b.branchNo
  AND  s.position = 'Manager'
  AND  b.city = 'London';
② Canonical (Unoptimized) Relational Algebra Expression Unoptimized

Translate SQL literally: Cartesian product first, then one big σ on top, π at root.

π* ( σs.branchNo=b.branchNo ∧ s.position='Manager' ∧ b.city='London' ( Staff × Branch ) )
Cost: Staff × Branch = 1000 × 50 = 50,000 rows created, then filtered. Very expensive.
③ Optimized Relational Algebra Expression Optimized

Apply Heuristics H1, H2, H3:

H1: Split AND conditions (Rule 1), push σs down (Rule 6)

σs.branchNo=b.branchNo ∧ s.position='Manager' ∧ b.city='London' splits into three σs.
σposition='Manager' involves only Staff → push it down to Staff.
σcity='London' involves only Branch → push it down to Branch.

H2: Replace σjoin_condition(A × B) with A ⋈ B

The condition s.branchNo = b.branchNo is a join predicate on a Cartesian product → replace with ⋈.

σposition='Manager'(Staff)  ⋈Staff.branchNo=Branch.branchNo  σcity='London'(Branch)
Cost now: Staff filtered to 50 Managers first. Branch filtered to 5 London branches first. Join of 50 × 5 = 250 rows — compared to 50,000 rows in the canonical form.
④ Draw Both Trees
Canonical (Unoptimized) Tree
Optimized Tree (after H1 + H2)
⑤ Write the Optimized SQL

The optimized RA tells you to filter before joining. Write SQL that reflects this: 

-- Original (canonical) SQL:
SELECT * FROM Staff s, Branch b
WHERE s.branchNo = b.branchNo AND s.position = 'Manager' AND b.city = 'London';

-- Optimized SQL (explicit subqueries mirroring the optimized RA tree):
SELECT *
FROM  (SELECT * FROM Staff  WHERE position = 'Manager') AS managers
  JOIN (SELECT * FROM Branch WHERE city = 'London')  AS london_branches
    ON  managers.branchNo = london_branches.branchNo;
Note: Modern SQL optimizers actually run both forms the same way — they internally apply the same heuristics. But writing the "optimized SQL" for the exam means explicitly placing filters in subqueries or CTEs before the join, to show the examiner that you understand the optimization.

Worked Example 2 — Three Tables (Example 23.3)

Query: "For prospective renters who are looking for flats, find properties that match their requirements and are owned by owner CO93."

① The SQL
SELECT p.propertyNo, p.street
FROM   Client c, Viewing v, PropertyForRent p
WHERE  c.prefType = 'Flat'
  AND  c.clientNo = v.clientNo
  AND  v.propertyNo = p.propertyNo
  AND  c.maxRent >= p.rent
  AND  c.prefType = p.type
  AND  p.ownerNo = 'CO93';
② Canonical RA Expression Unoptimized
πp.propertyNo, p.street (
  σc.prefType='Flat' ∧ c.clientNo=v.clientNo ∧ v.propertyNo=p.propertyNo ∧ c.maxRent≥p.rent ∧ c.prefType=p.type ∧ p.ownerNo='CO93' (
    (Client × Viewing) × PropertyForRent
  )
)
Big single σ on top of a double Cartesian product — worst possible strategy.
③ Optimization Steps

Step 1 — H1: Split σ and push down (Rules 1 + 6)

c.prefType='Flat' → push down to Client.
p.ownerNo='CO93' → push down to PropertyForRent.
c.clientNo=v.clientNo → join condition between Client and Viewing.
v.propertyNo=p.propertyNo → join condition between Viewing and PropertyForRent.

Step 2 — H2: Replace σjoin(× ) with ⋈

The two join conditions become ⋈ operators.

Step 3 — H3: Reorder joins (Rule 11) — most restrictive first

Assume fewer properties owned by CO93 than clients looking for flats.
So: PropertyForRent (filtered by ownerNo='CO93') should be joined first with Viewing, then with Client.

Step 4 — H4: Push π down (Rule 7)

Project out columns not needed at each stage to reduce intermediate result size.

Optimized RA Expression:

πp.propertyNo, p.street (
  σc.prefType='Flat'(Client)
    ⋈c.clientNo=v.clientNo ∧ c.maxRent≥p.rent ∧ c.prefType=p.type
      ( Viewing ⋈v.propertyNo=p.propertyNo σp.ownerNo='CO93'(PropertyForRent) )
)
④ Optimized RA Tree (3 tables)
Section 08

How to Draw a RA Tree — Step-by-Step Protocol

The Drawing Protocol (use for any exam question)
  1. Identify tables (FROM clause) → draw them as rectangles at the bottom (leaf nodes)
  2. Canonical tree: connect leaves with × nodes, put one big σ on top, then π at root
  3. Optimized tree: apply H1–H4 transformations, step by step, showing the tree change
  4. Labels: always write the full condition inside σ and π nodes
  5. Arrows: data flows upward — from leaf to root
  6. Left-deep form: in joins, always make the left child the result of a previous join and right child a base relation (this is the standard form)

Node Shape Conventions

σ
Selection — oval or rectangle, blue. Write condition as subscript.
π
Projection — oval or rectangle, green. Write column list as subscript.
⋈
Join — two children, write join condition. Left child is outer, right is inner.
Left-Deep Tree (the standard)
In a left-deep tree, every join node's right child is always a base relation (leaf). The left child is the result of a previous join. This is what most DBMSs use internally, and it's what you should draw in the exam unless told otherwise.
Section 09

⚡ Quiz Prep — Expected Questions

Q1: What is query optimization? What are the two main techniques?
Query optimization is the process of choosing the most efficient execution strategy for a query. The two techniques are: (1) Heuristic approach — applies transformation rules to reorder operations (push σ down, replace × with ⋈, etc.) and (2) Cost-based approach — estimates the I/O cost of different strategies and picks the cheapest one.
Q2: What is a canonical relational algebra tree?
The naive, direct translation of SQL into RA. It has all table relationships as Cartesian products (×) at the bottom, one large σ node with all WHERE conditions on top of the products, and a π node at the root. It is always unoptimized and expensive.
Q3: What is the most important heuristic in query optimization?
Perform Selection (σ) as early as possible — push it down the RA tree toward the leaf nodes. This reduces the number of rows in each relation before any join is performed, dramatically reducing the cost of subsequent binary operations like joins.
Q4: How do you convert a Cartesian product + Selection into a Join?
If a Selection predicate expresses a join condition (e.g., R.a = S.b) and it sits above a Cartesian product (R × S), replace the pair with a single Join: σR.a=S.b(R × S) = R ⋈R.a=S.b S. This is Heuristic 2 / part of Rule 6.
Q5: What is the difference between materialization and pipelining?
Materialization: the intermediate result of one RA operation is written to a temporary relation on disk, and the next operation reads from it. Pipelining: the result tuples of one operation are passed directly to the next operation without creating a temporary disk relation — saving I/O cost.
Q6: What is a left-deep tree and why is it preferred?
A left-deep join tree is one where the right child of every join node is always a base relation (a table), while the left child is the result of a previous join. It is preferred because: (1) it reduces the optimizer's search space, (2) it allows the use of dynamic programming algorithms, and (3) it allows fully pipelined execution — inner relations are always base tables (already materialized).
Q7: Write the RA expression for: "Find all staff (name, salary) in branch B003 with salary > 15000"
Canonical: πfName,lName,salary( σbranchNo='B003' ∧ salary>15000(Staff) )

Optimized: Same in this case — it's a single table, so push both conditions directly: πfName,lName,salary( σbranchNo='B003'( σsalary>15000(Staff) ) )

Optimized SQL:
SELECT fName, lName, salary FROM Staff WHERE branchNo = 'B003' AND salary > 15000;
Q8: What are the 5 heuristics in order?
H1: Perform Selection (σ) as early as possible — push down.
H2: Replace σjoin condition(R × S) with R ⋈ S.
H3: Reorder joins using associativity — most restrictive (smallest result) first.
H4: Perform Projection (π) as early as possible — push down.
H5: Compute common sub-expressions once and cache the result.
Q9: What is static vs dynamic query optimization?
Dynamic: query is parsed, validated, and optimized every time it runs — always uses up-to-date statistics but has runtime overhead. Static: query is optimized once (like a compiler), plan is reused — no runtime overhead but the plan may become suboptimal if the data changes significantly. Most systems use a hybrid approach.
Q10: For a 3-table query, write the template for an optimized RA tree
πoutput_columns (
  σfilter on T1(T1)
    ⋈T1.key=T2.key ∧ extra conditions
      ( T2 ⋈T2.key=T3.key σfilter on T3(T3) )
)

Key points: σ is pushed down to individual tables, ⋈ replaces ×, most selective join is innermost.

Query optimization — choosing the best execution plan
Canonical tree — naive, unoptimized RA tree
σ (Selection) — filters rows (= WHERE)
π (Projection) — picks columns (= SELECT)
⋈ (Join) — combines tables on condition
× (Cartesian product) — all rows × all rows
Heuristic — rule of thumb, not guaranteed optimal
Left-deep tree — right child always a base table
Pipelining — pass results between ops without disk write
Materialization — write intermediate result to disk

Push π down — drop columns early, before joins
